# TB01 底盘控制固件 — 达妙 DM-H65 桥

STM32F103 两驱差速底盘控制器。分支 **`damiao-bridge`**。

固件只做两件事，**故意不做第三件**：

1. **忠实执行上位机命令** —— 车体速度 `(vx, wz)` → 差速逆解 → 达妙速度模式 CAN 帧；
2. **忠实上报电机状态** —— 轮速/扭矩/位置/温度/故障码/反馈年龄 + IMU 六轴。

> **不做**：轮速闭环、助推、偏航捕获、自检点动、里程计、EKF。
> 航向保持与定位都在上位机（RK3576 / ROS 2）。责任边界见
> [`docs/division-of-labor.md`](docs/division-of-labor.md)（该文档写于 FOC 时代，
> 但"底盘只做忠实执行器"这条结论对现在依然成立）。

```
┌──────────────┐  USB 115200  ┌────────────────┐  CAN 1 Mbps  ┌─────────────────┐
│   RK3576     │◄────────────►│     STM32      │◄───────────►│ 达妙 DM-H65 ×2   │
│ ROS 2 humble │   CH340      │  F103 底盘板   │  PA11/PA12   │ 左#2 / 右#1      │
└──────────────┘  PA9/PA10    └────────────────┘  标准帧       └─────────────────┘
                                     │
                    PB9  ────────────┴── 心跳灯（500 ms 翻转，只表示主循环活着）
                    PB10/PB11 ─────────── 亚博 YbImu（软件 I2C，地址 0x23）
```

## 1. 车型（两辆车共用这一份固件）

两辆车**只有轮距不同**，电机、CAN、协议、IMU 全部一样。轮距由 **Keil target 的编译宏**
`TRACK_WIDTH_MM` 传入，`main.c` 里**没有默认值** —— 不传就直接 `#error` 编不过。

| | 扫地车 `sweeper` | 洗地车 `scrubber` |
|---|---|---|
| 电机 | 达妙 DM-H65 (DM6540-1EC) | 同款 |
| 轮径 | 171 mm | 171 mm |
| **轮距** | **716 mm** | **456 mm** |
| 编译宏 | `-DTRACK_WIDTH_MM=716` | `-DTRACK_WIDTH_MM=456` |
| 产出 | `Objects/sweeper/sweeper.hex` | `Objects/scrubber/scrubber.hex` |

**几何、换算系数、加新车型的步骤、以及"怎么在车上验证烧的是哪个车型"，
全部在 [`docs/vehicle-params.md`](docs/vehicle-params.md)。**

> ⚠️ **轮距写错是安全级错误**：转向增益会差 `716/456 = 1.570` 倍，
> 而**直行完全不受影响** —— 低速直线测试会"看起来正常"，问题只在转弯和导航时暴露。

## 2. 关键参数（`firmware/stm32-chassis/user/main.c`）

| 宏 | 值 | 说明 |
|---|---|---|
| `WHEEL_R_M` | `0.0855f` | 轮半径，171 mm 轮径的一半（两车相同） |
| `TRACK_WIDTH_M` | `TRACK_WIDTH_MM/1000.0f` | **由 target 传入**，无默认值 |
| `MAX_OMEGA_RAD_S` | `30.0f` | 单轮角速度上限 ≈ 2.565 m/s |
| `DM_DIR_LEFT` / `DM_DIR_RIGHT` | 按车型 | 左右轮方向系数，**按 `VEHICLE_SEL` 分车型**；命令侧和反馈侧都乘 |
| `CTRL_PERIOD_MS` | `20` | 控制/下发周期 50 Hz |
| `STATUS_PERIOD_MS` | `50` | 状态上报 20 Hz |
| `CMD_TIMEOUT_MS` | `800` | 上位机命令超时 → **只清零，不失能** |
| `RAMP_VX_ACC` / `RAMP_VX_DEC` | `1.0f` / `0.80f` m/s² | **缓起缓停**（线速度斜坡，固件内做；0.20 m/s 起步 200 ms / 停下 250 ms） |
| `RAMP_WZ_ACC` / `RAMP_WZ_DEC` | `4.0f` / `1.5f` rad/s² | 同上，角速度斜坡 |
| `RAMP_TIMEOUT_DEC` | `0.70f` m/s² | **仅 `CMD_TIMEOUT_ENABLE=1` 时用**：命令超时的软停斜率（wz 用 `RAMP_TIMEOUT_WZ_DEC 2.5`） |
| `CMD_TIMEOUT_ENABLE` | `0` | **0 = 命令锁存**（没新命令就一直按最后一条跑）；1 = 超时清零 |
| `FB_TIMEOUT_MS` | `2000` | 电机反馈超时 → 标 offline + 目标清零 |
| `STATUS_VERSION` | `8` | 诊断帧 `[30]`：v2 功能帧 `0x06`、v3 心跳（已删）、v4 命令锁存、v5 洗地车辅助按钮、v6 辅助按钮默认 1000→200 ms、v7 辅助按钮极性修正（驱动低边 MOS 栅极）、**v8 新增独立功能帧 `0x7A`**（既有帧格式不变） |
| CAN | 1 Mbps，**标准帧** | 达妙协议，不是旧 FOC 的 500k 扩展帧 |

**为什么不失能而是清零**：达妙驱动器**失能后不制动**（转子 3.15 kg 会自由滑行）。
要停车必须主动发 `v_des = 0`，让驱动器自己去减速。`CMD_TIMEOUT` 只把目标清零。

**缓起缓停在哪一层做**：在**固件**里（`Control_Tick` 的 `Ramp_Step`），逆解之前先把
`vx`/`wz` 按斜坡推到目标，所以对所有上层（ROS / 网页 / 手动 CAN）一律生效。
为什么不用驱动器自带的 `ACC(0x04)`/`DEC(0x05)`：那两个寄存器出厂默认值未知、我们
从未写过，而且只有一组斜率、现场不方便调。二者可叠加使用（驱动器侧当兜底）。
`RAMP_ON_TIMEOUT=0` 的语义：**正常速度变化（含上位机主动发 0）走斜坡，命令超时仍立即归零**。

> ⚠️ **左右轮方向系数是分开的**（轮毂电机左右镜像安装）。扫地车
> `DM_DIR_LEFT=+1 / DM_DIR_RIGHT=-1`，洗地车两个都 `-1`，由 `VEHICLE_SEL` 选择。
> 典型症状：**按左转→车往前走、按前进→原地打转** = 某一侧系数反了，
> 不是混控公式错。判定方法见 `docs/vehicle-params.md` §4.1。

## 3. 串口协议（UART 115200，上行 2 帧 + 下行 2 帧）

**下行（主机 → STM32）**：速度指令帧 `0x7B`（11 字节，20~30 Hz 连续流）+
功能帧 `0x7A`（8 字节，偶发事件，见 §3.1.2）。
固件用"看帧头决定长度"的逐字节状态机解析，两种帧可任意穿插，
一个字节都不同步错也能自己找回来（`Cmd_FrameNeed()` / `Cmd_FeedByte()`）。

**上行（STM32 → 主机）**：遥测帧 `0x7B`（24 B）+ 诊断帧 `0x7E`（44 B）。

发送顺序固定：先 24 B 遥测（`0x7B`），再 44 B 诊断（`0x7E`），这样诊断帧尾正好给下一个遥测帧当头。

### 3.1 速度指令帧（主机 → STM32，11 字节）

| 偏移 | 长度 | 类型 | 内容 |
|---|---|---|---|
| 0 | 1 | uint8 | 帧头 `0x7B` |
| 1 | 1 | uint8 | AutoRecharge（**忽略**） |
| 2 | 1 | uint8 | SecurityPLY（**忽略**） |
| 3–4 | 2 | int16 **BE** | `vx * 1000`（mm/s） |
| 5–6 | 2 | int16 BE | `vy * 1000`（差速车**忽略**） |
| 7–8 | 2 | int16 BE | `wz * 1000`（mrad/s） |
| 9 | 1 | uint8 | `BCC = XOR(f[0]..f[8])` |
| 10 | 1 | uint8 | 帧尾 `0x7D` |

特殊：**`f[1]` 是功能码**，不只 `0x00` 才是速度帧：

| `f[1]` | 含义 | 行为 |
|---|---|---|
| `0x00` / `0x01` | 普通速度帧（`0x01` 是旧协议回充标志，本固件忽略） | 取 `f[3..4]`/`f[7..8]` 作为目标 |
| `0x06` | `FUNC_MOTOR_REINIT` | 重新"写速度模式 + 使能"；**只在车已停时接受** |
| `0x08` | ~~`FUNC_HEARTBEAT`~~ | **已废弃**（2026-11-07 移除）：现在被当普通速度帧处理，全零负载 = 清零目标 |
| `0x09` | `FUNC_AUX_BTN`（旧） | **仅兼容**（v5~v7 的老写法）：`f[2]`=掩码、`f[3]`=保持时间×10 ms。**新代码请用独立功能帧 `0x7A`（见 §3.1.2）**；速度帧 `0x7B` 的解析没有为它做任何改动 |

### 3.1.1 看门狗与停车语义（2026-11-07 定稿：**命令锁存，不自己停**）

★ **没收到新命令，就一直执行最后一条命令，不会自己停**
（用户定稿："没收到命令，就一直按上一次的命令执行，不要停"）。
固件 `CMD_TIMEOUT_ENABLE = 0`，命令看门狗**关闭**；目标只在收到新帧时更新。

| 触发 | 动作 |
|---|---|
| 上位机发新目标 | 加速 1.0 m/s²（wz 4.0），减速 **0.80** m/s²（wz 1.5） |
| 上位机发 0 目标（键盘 `k` / 页面松手 / cmd_vel=0） | **软停**（0.80 m/s²），保持使能 |
| 任一电机反馈掉线（`FB_TIMEOUT_MS = 2000`） | **急停**（唯一瞬停入口，目标强制 0） |
| 800 ms 没有新命令 | **什么都不做**（继续按最后一条命令跑） |

诊断帧 `[41]` **bit6 = 1** 表示"命令锁存"（无看门狗），`[30]` 版本号 = **4**。

> ⚠️ **风险**：上位机进程崩了、串口线掉了、电脑关机 —— 车会一直按最后一次速度
> 跑下去，直到电机反馈掉线或有人断电。想要"看门狗"语义就把
> `CMD_TIMEOUT_ENABLE` 改回 1（代码分支都在，超时减速用 `RAMP_TIMEOUT_DEC 0.70`）。
>
> 历史：1.5.0 加过"心跳帧 `f[1]=0x08` + 目标锁存（300 ms 链路看门狗）"，
> 因为键盘松手不停而被移除（2026-11-07），见
> [`docs/archive/ros-heartbeat-howto-removed.md`](docs/archive/ros-heartbeat-howto-removed.md)。

### 3.1.2 洗地车辅助按钮（PB0 / PB1，独立功能帧 `0x7A`，固件 v8+）

> 协议演进：v5 把命令塞进速度帧的 `f[1]=0x09`；**v8 起改成独立的功能帧 `0x7A`**
> （速度帧是 20 ms 一拍的高频流，按按钮是偶发事件，分开后互不干扰；
> 服务端解析器也换成了通用的"看帧头决定长度"状态机，速度帧一个字节没动）。
> 老写法仍然兼容，但新代码请用 `0x7A`。

**硬件（原理图）**：`PB0 → R7 220Ω → Q1 栅极（AO3400A，源极接地，漏极→U8.1）`，
`PB1 → R8 220Ω → Q2 栅极（AO3400A，源极接地，漏极→U8.2）`，
`U8 = WAFER-PH2.0-2PLB`（3/4 脚接地）。也就是说这两路**本身就是低边开漏开关**，
固件只需要驱动 MOSFET 栅极：

```
栅极高(3.3V) → 管子导通 → 对方那条按钮线被拉到 GND = "按下"
栅极低(0V)   → 管子关断 → 线路悬空，对方上拉回 3.3V = "松开"
```

★ **逻辑是反的**：输出高 = 按下，输出低 = 松开。空闲必须是
**推挽输出低**（主动把栅极拉到 0），**绝不能用上拉输入** ——
上拉输入会把栅极抬到 3.3V → 管子常通 → 对方按钮线永久被按在 GND
（v6 就是这么翻车的：一插线对方引脚就变 GND，2026-11-07 修）。

上位机发一条**独立功能帧**（8 字节，自己的帧头 `0x7A`）后，固件把指定按钮的栅极拉高、保持
`p1×10 ms`（默认 **200 ms**、范围 30~5000 ms；200 ms 就是按一下普通按钮的手感，太长对方会当成"长按"）
后**自动拉低**：

```
7A <func> <p0> <p1> <p2> <p3> <BCC> 7D        BCC = XOR(f[0] … f[5])

func = 0x01       按一下辅助按钮
p0   = 掩码       1 = PB0(刷盘)，2 = PB1(风机)，3 = 两个一起
p1   = 保持时间   单位 10 ms；0 = 用固件默认 200 ms（范围 30~5000 ms）
p2/p3 = 保留，填 0
```

功能帧**不刷新速度看门狗、不改变速度目标**：发完车该怎么跑还怎么跑
（`Func_Apply()` 只调 `AuxBtn_Trigger()`，不碰 `g_cmd_vx_mm / g_cmd_wz_mrad / g_last_cmd_ms`）。

**两个按钮分别是干什么的**（对方主板上的一对自锁式轻触键，按一下就切换一次）：

| 掩码 | 引脚 | 功能 | 说明 |
|---|---|---|---|
| `0x01` | PB0 | **开关刷盘**（brush） | 发一次 = 按一下 = 刷盘状态翻转一次 |
| `0x02` | PB1 | **开关风机**（fan） | 发一次 = 按一下 = 风机状态翻转一次 |
| `0x03` | PB0+PB1 | 两个同时按 | 一般不用 |

**可以直接抄的字节**（8 字节功能帧，含 BCC）：

| 干什么 | 十六进制 | 说明 |
|---|---|---|
| 按一下刷盘（默认 200 ms） | `7A 01 01 00 00 00 7A 7D` | `p0=0x01`、`p1=0` 用默认时长 |
| 按一下风机（默认 200 ms） | `7A 01 02 00 00 00 79 7D` | `p0=0x02` |
| 按一下刷盘 500 ms | `7A 01 01 32 00 00 48 7D` | `p1=50`（×10 ms） |
| 按一下风机 500 ms | `7A 01 02 32 00 00 49 7D` | |
| 两个一起（默认 200 ms） | `7A 01 03 00 00 00 78 7D` | |

`BCC = XOR(f[0] … f[5])`，两帧之间不用加别的分隔符（帧头 `0x7A`/`0x7B`、帧尾 `0x7D` 已经能自同步）。
解析器按帧头决定长度（`0x7B`→11 字节、`0x7A`→8 字节），两种帧可以任意穿插。

> 老写法（固件 v5~v7，仍兼容）：`7B 09 <mask> <hold> 00 00 00 00 00 <BCC> 7D`，
> BCC = XOR(f[0]…f[8])。例：按一下刷盘 `7B 09 01 00 00 00 00 00 00 73 7D`。

★ **我们这侧只有输出、没有输入**：只能"按一下"，读不到对方刷盘/风机到底开着还是关着。
所以**真正的开关状态要上位机自己记账** —— 发一次就是把该功能翻转一次；
如果上位机中途重启、丢了记账，就会反向（按两次按钮就又对了）。
诊断帧 `[39]` 只回读"我们这一侧确实按了"（bit3 正在按 / bit4 最近按过刷盘 / bit5 最近按过风机），
不代表对方的开关状态。

| 触发方式 | 怎么发 |
|---|---|
| 网页（`car_web` 1.6.2+） | 页面"洗地车辅助按钮 → 按 PB0（刷盘）/ 按 PB1（风机）"（旁边可选按下时长 100/200/300/500/1000 ms，默认 200），或 `POST /api/aux_btn {"mask":1,"hold_ms":200}`、WS `{"t":"aux_btn","mask":1}` |
| 直连串口（自研上位机） | 自己往 `/dev/ttyUSBx` 写上面那 8 字节；或抄 `tools/car_web/car_web.py` 的 `build_aux_func_frame()` / `build_func_frame()`（`tools/aux_btn_test.py` 里也有同名实现，加 `--legacy` 发旧的 11 字节写法） |
| `car_web` 的 HTTP | `POST http://<主机>:8000/api/aux_btn`，body `{"mask":1,"hold_ms":200}`（`mask` 1=刷盘 2=风机；`hold_ms` 省略或 0 = 固件默认 200 ms） |
| ROS（厂商 `wheeltec_robot_node`） | **发不了**：它只发 11 字节速度帧；要在 ROS 里用，得自己在节点里加一条写 `0x7A` 功能帧的代码（该节点串口只允许一个写者，别从外部抢） |

要点：

- **功能帧独立于速度帧**：8 字节、帧头 `0x7A`，速度帧（`0x7B`，11 字节）一个字节没动；
  两种帧可以任意穿插，解析器按帧头决定长度（`Cmd_FrameNeed()`）。
- **功能帧不改变速度目标**，车该怎么跑还怎么跑（`Func_Apply()` 只调 `AuxBtn_Trigger()`）。
- 回读在诊断帧 `[39]`：**bit3 = 正在按**、bit4 = 最近按过 PB0、bit5 = 最近按过 PB1
  （`car_web` 的 `/api/state` 里是 `aux.active / aux.pb0 / aux.pb1`）。
- **扫地车没有这个功能**（`VEHICLE_SEL != 2` 时是空实现，帧被安全吃掉）。
- `AuxBtn_Init()` 在 `main()` 里是**第一条**初始化语句：复位后引脚浮空，
  栅极可能保持着高电平 → 管子常通；先把它拉低再去初始化别的。
- 引脚复用自旧继电器宏（`RELAY_*` 已删除），见 `main.c` 的"辅助按钮输出"一节。
- **发一次就够，不要连发**：对方是自锁开关，按一下就翻转一次；连发两帧 = 开 + 关。
  同一按钮两次操作至少间隔 `hold + 200 ms`。

### 3.2 主遥测帧（STM32 → 主机，24 字节）

兼容厂商 `wheeltec_robot_node`（它**只**解析这一帧），字段与它逐一对齐：

| 偏移 | 内容 |
|---|---|
| 0 | 帧头 `0x7B` |
| 1 | `Flag_Stop` |
| 2–3 | `vx`（mm/s，int16 BE） |
| 4–5 | `vy` |
| 6–7 | `wz`（mrad/s） |
| 8–13 | accel 三轴 int16 BE（m/s² = raw / 1671.84） |
| 14–19 | gyro 三轴 int16 BE（rad/s = raw × 0.00026644） |
| 20–21 | 电池 mV（**本板无采样，恒 0**） |
| 22 | `BCC = XOR([0..21])` |
| 23 | 帧尾 `0x7D` |

### 3.3 扩展诊断帧（STM32 → 主机，44 字节，`0x7E`）

厂商节点**不解析**这一帧（安全，随便改），用来查"轮子到底有没有劲"。
布局和字段含义见 [`docs/chassis-serial-protocol.md`](docs/chassis-serial-protocol.md)；
在线解码工具：

```powershell
python tools/decode_diag.py --port COM3
```

关键字段：目标/实际 ω、扭矩 Nm、位置、ERR 码、MOS/线圈温度、
**左右反馈年龄**、CAN 失败计数、启动阶段、`[30]` 版本号（**v6**）、
`[39]` bit0-2 IMU 体检 + **bit3/4/5 辅助按钮** + bit7 陀螺读到过、
`[41]` 低 3 位启动阶段 + bit6 命令锁存（bit7 保留位）。

> 达妙反馈的是**扭矩 Nm**，不是电流 A。固件没读 KT 寄存器，**所以不显示电流、
> 也不做换算**（换算出来是编的）。

## 4. 编译与烧录

工程：`firmware/stm32-chassis/stm32-chassis.uvprojx`

**★ 工程里有两个 target，选 target 就是选车型 —— 不用改源码：**

| Keil target | 车型 | 轮距 | 产出 hex |
|---|---|---|---|
| `sweeper` | 新扫地车 | **716 mm** | `Objects/sweeper/sweeper.hex` |
| `scrubber` | 洗地车 | **456 mm** | `Objects/scrubber/scrubber.hex` |

两个 target 的唯一差别就是编译宏（`TRACK_WIDTH_MM`），源码是同一份。
**每个 target 必须有自己的独立输出目录**，否则 `.o` 互相覆盖 —— 见
[`docs/archive/README-foc-era.md`](docs/archive/README-foc-era.md) 里
"2026-10-12 烧错固件"那节（真事，导航跑飞过）。

命令行编译（UV4 是 GUI，必须等它退）：

```powershell
Start-Process -FilePath "D:\Keil\UV4\UV4.exe" `
  -ArgumentList '-b','-r','stm32-chassis.uvprojx','-t','sweeper','-o','build.log' -Wait
```

验收门槛：日志里 **`0 Error(s), 0 Warning(s)`**，当前 Code ≈ 11392 B。

**烧录前必读**：车轮架空 **或** 驱动器断电。历史上在地面带载烧录时
发生过底盘原地暴冲（目标被夹到上限、单轮 −40 A），这条不能破。

**烧完怎么确认车型对不对**（别信标签，看书据）：

```powershell
# ① 两个 hex 的 MD5 必须不同
(Get-FileHash Objects\sweeper\sweeper.hex  -Algorithm MD5).Hash
(Get-FileHash Objects\scrubber\scrubber.hex -Algorithm MD5).Hash
```

② 车上验证：车轮架空，发 `vx=0, wz=+0.30`，读诊断帧 `[10..11]`/`[12..13]` 目标 ω：
**sweeper `+126/−126`，scrubber `+80/−80`**。详见 `docs/vehicle-params.md` §4。

## 7. 排查顺序（车不动时）

1. **串口有没有帧**：`python tools/decode_diag.py --port COM3` 能收到 20 Hz 帧吗？
   - 收不到 → 先看 `lsusb` 有没有 `1a86:7523`（CH340）。**没有就是物理层**
     （线没插 / 线是充电线 / STM32 没上电），此时改代码无用。
2. **电机使能了吗**：诊断帧 `[18]`/`[19]` 的 ERR 应是 **1（使能）** 或 0（失能）。
   - 一直是 0 → 上电时使能帧丢了。发功能帧 `0x06`（`FUNC_MOTOR_REINIT`）重新使能，
     或复位 STM32（**必须在驱动器已上电稳定之后**复位）。
3. **目标 ω 有没有**：`[10..11]`/`[12..13]` 非零吗？
   - 零 → 上位机没在发命令，或命令看门狗超时（`flags` bit4）。
4. **实际 ω 跟不跟**：目标 vs 实际差距大 → 看扭矩、温度、ERR 码。
   - 架空实测跟随度 **99.4 %**（目标 −3.50 / 实际 −3.48 rad/s），跟不住就是真问题。
