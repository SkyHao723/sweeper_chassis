# sweeper_chassis — 两驱差速清扫车底盘

STM32 底盘控制器 + FOC 驱动器 CAN 总线，上位机是 **RK3588**（ROS 2）。

**只有一个上位机，也只有一个固件。** 定位（卡尔曼滤波）在上位机做，
STM32 只管运动学、CAN 下发、看门狗、继电器和状态上报。

```
┌──────────────┐  USB 115200  ┌────────────────┐  CAN 500k  ┌──────────────┐
│    RK3588    │◄────────────►│     STM32      │◄──────────►│ FOC 驱动器 ×2 │
│  ROS2 + EKF  │  CH340       │  (底盘控制器)   │  PA11/PA12 │  1号 / 2号    │
└──────────────┘  PA9/PA10   └───┬────────┬───┘            └──────────────┘
                                 │        │
                            PB0 ┌▼┐   PB1 ┌▼┐
                                滚刷继电器  水泵继电器

                        PB10/PB11 ── 亚博 YbImu（软件 I2C）
```

> 早期用 ESP32 网页遥控当临时上位机调试，**已废弃并从仓库移除**。
> STM32 上对应的 USART2 / 双口控制权仲裁 / 本地 EKF 也一并删掉了。

## 分工

| 谁 | 干什么 |
|---|---|
| **STM32** | 解析车体速度 `(vx, vy, wz)` → 差速逆解 → CAN 下发；轮速正解 + 读 IMU → 上报；看门狗；继电器 |
| **RK3588** | 真正的上位机：ROS 2 + EKF + 导航。接 STM32 的 USART1（PA9/PA10）|

**为什么 EKF 不在 STM32 上**：算力放在上位机，换车/改模型只改一处；
STM32 也不必为了滤波去背一堆浮点矩阵。本仓库历史上确实在 STM32 上跑过
EKF（配合网页画轨迹），ESP32 退场时一起删了，需要的话在 git 历史里找。

## 快速开始

### 接线

**先读 [`docs/wiring.md`](docs/wiring.md)**，里面有全部引脚、电源要求和排错顺序。

最容易踩的三个坑：

1. **所有板子必须共地**（继电器不共地会持续嗡嗡响）
2. **串口 TX/RX 要交叉接**（TX 接对方的 RX）
3. **CAN 收发器选 3.3V 的**（SN65HVD230），TJA1050 是 5V 的，直连 PA11 有风险

### 编译烧录 STM32

```
firmware/stm32-chassis/stm32-chassis.uvprojx
```

Keil MDK 打开它，用 **ST-Link (SWD)** 烧录。SWD 占用 PA13/PA14，和串口不冲突。
产出 `Objects/stm32-chassis.hex`。目前 Code ≈ 10400 B / 0 Error / 0 Warning。

## 底盘参数

在 `firmware/stm32-chassis/user/main.c` 顶部，**换车必须重新标定**：

```c
#define WHEEL_DIAMETER_MM   205.0f   /* 车轮直径 */
#define TRACK_WIDTH_MM      930.0f   /* 左右轮触地间距 */
#define MAX_RPM             200      /* 单轮转速上限 */

#define MOTOR1_IS_LEFT      1        /* 1号电机在左侧 */
#define MOTOR1_INVERT       0        /* 某个轮子转向相反时改成 1 */
#define MOTOR2_INVERT       1        /* 实测 2 号电机正方向是反的 */

#define ACCEL_STEP_MS       0        /* 加速间隔 ms/1RPM, 0=阶跃, 见下 */
#define DECEL_STEP_MS       0        /* 减速间隔, 停车安全优先, 保持 0 */
```

方向不对照着 `docs/wiring.md` 的校准表改，别硬调混控逻辑。

### 加减速斜坡：现在是 0（阶跃），别再凭直觉加

命令帧里的 `DATA4/DATA5` 是**加减速间隔**，单位是「每变化 1 RPM 花多少毫秒」，
范围 0~100，0 = 阶跃。

**曾经改成 3**（想让起步柔和、少顶过流保护），但一直没做 A/B。后来补上对比，
同一条 0.30 m/s 直线：

| | 斜坡=3 | 斜坡=0（现在）|
|---|---|---|
| 稳态速度 | 68%~137% 乱跑 | **86%**（全程=稳态）|
| 到 80% 速度 | 0.15~0.80 s | 0.40 s |
| 直线漂移 | ~20°/m | **−5.4°/m**（1.54 m 偏 8.3°）|

**漂移改善约 4 倍。** 机理猜测：斜坡让驱动器的设定值缓慢爬升，而驱动器速度环
本身就在低频振荡（空载实测：目标 18 RPM 时实际在 0~22 之间来回冲），设定值
慢慢追会让两者互相激励、振得更厉害；改回阶跃后环反而更容易稳住。

**想再加斜坡之前先做 A/B，别凭直觉**；也别指望它改善准确度 —— 它本来是为了柔顺。
减速也保持 0：要停就立刻停，停车安全优先。

> 起步迟钝的**真正**原因不是斜坡，是轮胎刮擦/静摩擦（见下面"轮速外环修正"）。
> 斜坡只会雪上加霜。

### 轮速外环修正（trim）

STM32 原来是**纯开环**：算完目标轮速直接发给驱动器，从不回读实际转速。所以
驱动器没做到位它也不知道。实测（2026-09，原地转，车在实地）：

| 命令 wz | 单轮目标 | 第 0 秒 | 第 1 秒 | 第 2 秒 | 稳态 | 四秒总角度 |
|---|---|---|---|---|---|---|
| 0.30 | 13 RPM | 5% | 15% | 89% | 85% | 49% |
| 0.50 | 22 RPM | 1% | 29% | 20% | 115% | 41% |
| 0.70 | 30 RPM | 10% | 86% | 121% | 106% | 81% |
| 1.00 | **43 RPM** | **26%** | 106% | 100% | 96% | 82% |

**即使目标高达 43 RPM，第 0 秒也只有 26%** —— 而直线运动 0.07 秒就到 80%。
同一个轮速区间差这么多，说明这**不是**驱动器低速死区，而是**原地转要克服轮胎
刮擦/静摩擦**：轮子是真的没转（不是空转打滑），所以把指令顶上去它就会转。

#### 第一版：纯积分 + 绝对限幅（已废弃，别重犯）

第一版是"纯积分 + 绝对限幅 ±30 RPM + `TRIM_KI=1.5`"。四秒总角度确实从
41%~82% 提到了 85%~98%，稳态也从 115% 回到 101% —— **但形状和安全性都不合格**：

- **绝对限幅在小名义值下会把指令顶成反向。** 原地转 `wz=0.30` 的名义轮速只有
  13 RPM，而修正量能到 -30，于是 `指令 = 13-30 = -17`，**轮子反转**。干净重测的
  逐秒数据 `0.025 / 0.585 / 0.573 / -0.001` 里第 3 秒直接归零，就是它。
  一个"修正"把自己修成了故障。
- **`TRIM_KI=1.5` 太快，和驱动器那个环组成了慢速极限环。** `wz=1.00` 的逐秒是
  `0.386 / 1.746 / 0.867 / 0.529`：第 1 秒过冲 175%，然后一路衰减下去。
  积分增益 × 被控对象滞后 > 1 就会这样。
- 第一版注释里写的"输出永远落在普通全速命令能到的范围内"是**错的**：
  `MAX_RPM` 是 200，而 ±30 的绝对限幅在名义值 13 时已经把指令推到 2~3 倍了。

#### 第二版（现在）：慢积分 + 比例限幅 + 定时助推

```c
#define TRIM_ENABLE        1
#define TRIM_KI            0.6f     /* 慢积分, 只修稳态偏差 */
#define TRIM_UP_K          0.5f     /* 正向最多 +50% 名义值 */
#define TRIM_DOWN_K        0.5f     /* 反向最多 -50% 名义值 -> 永不反转 */
#define TRIM_MAX_RPM       20.0f    /* 绝对上限, 防高名义值下修正量过大 */
#define TRIM_DEADBAND_RPM  0.5f

#define KICK_RPM           12.0f    /* 起步助推幅度 */
#define KICK_MS            400      /* 助推的硬上限时长(轮子一直没起来才用满) */
#define KICK_RELEASE_K     0.6f     /* 轮速达到名义值的这个比例就撤掉助推 */
#define KICK_REARM_MS      300      /* 目标归零后静止这么久才允许再次助推 */
```

三条改动逐条对症：

1. **限幅改成按名义值的比例**，不用绝对值 —— 于是指令永远落在 `[0.5, 1.5]` 倍
   名义值之内，**方向永远不变**。反转从机制上被消除。
2. **`TRIM_KI` 降到 0.6**，让它只修稳态偏差，不去和驱动器那个环抢动态。
3. **起步助推单独做。** 突破静摩擦需要的是"立刻给力"，而积分天生要"等误差攒
   起来"；把积分调到能立刻给力，它就会在轮子追上来之后迟迟不回，那正是第一版
   的过冲。两件事分开：**积分慢而稳只管稳态，助推开环/定时/有界只管起步这一下**
   —— 开环所以不构成第二个反馈回路，也就不会振。
   助推幅度取固定值而不是按名义值缩放：要突破的是**摩擦力矩**，它跟打算跑多快
   没关系，所以固定的一脚在低速档反而相对更有力，正是需要的。

#### 助推必须"轮子一转起来就撤"，不能只靠定时

第一版助推是**固定 400 ms**。原地转（真需要助推）表现很好，但**直线运动被它害了**：
直线没有静摩擦问题，轮子 0.06 秒就起来了，此时还在助推就是纯超速 ——
`decode_diag --drive 0.30 0` 对应的稳态从 103% 变成 144%，而
`144% ≈ 名义值 + 助推`，对得上。

助推是给"**卡住**"用的，所以判据应该是"轮子还没转起来"，不是"时间没到"。
现在 `KICK_RELEASE_K=0.6`：实际轮速一到名义值的 60% 就立刻撤掉，`KICK_MS` 只作为
兜底上限。原地转的轮子被刮擦卡住（实际远低于名义值）→ 助推给满；
直线运动的轮子秒起 → 助推一个周期内就撤掉。

**安全性**（按"绝不引入新的失控模式"设计）：

1. 指令永远落在 `[1-TRIM_DOWN_K, 1+TRIM_UP_K]` 倍名义值之内（助推另加，且助推
   有时长上限），**方向不变**。
2. **目标为 0 时 `Trim_Apply` 恒定返回 0**，修正和助推一起清零、不留历史 ——
   外环**不可能**在主机下令停车的时候把车带着走。这是敢上车的底线。
3. 最后还有一条独立的保险：名义为正就保证输出 ≥ 0，反之亦然。即使上面的限幅
   哪天被人改错，这条也能兜住。
4. 驱动器回码不新鲜时不积分、只保持 —— 拿旧数据积分会把修正量喂到限幅。
5. **里程计不受影响**：`Wheel_Update()` 用的仍是驱动器回传的实际转速，外环只改
   下发值，所以上报给上位机的轮速依然诚实。
6. 积分用的是**真实周期**（从 `g_tick_ms` 算），不是标称的 20 ms —— 否则
   `TRIM_KI` 的实际含义会随主循环负载漂移，参数就没法标定了。

**怎么看它在不在干活**：诊断帧里上报的"目标"是**含修正的最终命令**。用 `--drive`
时脚本知道主机下发的理论目标，会自动把修正量还原出来：

```bash
# ★ 跑之前必须先暂停看门狗! 否则它会把 ROS 节点反复拉回来抢串口（见"已知的坑"）
touch /tmp/chassis_watchdog.pause
# 然后停掉 ROS 底盘栈 (Ctrl-C), 再:
python3 tools/decode_diag.py -p /dev/wheeltec_controller --drive 0 0.5
# 输出里会多出一段:   外环修正+18/+25
rm /tmp/chassis_watchdog.pause     # 调完一定要删!
```

理想波形：起步那 0.4 秒应该能看到 `外环修正` 明显为正（助推在起作用），轮子转
起来之后回落到 0 附近；全程**不应**看到指令变号，也不应看到修正量贴着限幅不放。

**调参**：起步还是慢就先加 `KICK_RPM`（每次 +4 RPM 试）；如果看到轮速以
0.1~0.2 Hz 慢速来回摆，说明积分还是太快，降 `TRIM_KI`。想 A/B 就把
`TRIM_ENABLE` 改成 0 重新编译。

> ⚠️ `decode_diag.py` 显示的"**目标-理论**"= 积分修正 **+ 助推** 的合计。
> 实测被它骗过一次：看到 `+13` 以为积分已经顶到比例限幅（±13.95）了，其实
> 其中 12 是助推、积分只剩 1，判断完全反了。想分开看只能改协议（诊断帧没有
> 空余字节），暂时按合计显示。

#### 还没解决：直线精度的锅不在外环，在驱动器自己的速度环

用 `decode_diag --drive 0.30 0` 逐帧看（这是唯一能看到外环内部的途径）：

```
目标 +35  实际  +0   +7.80A     ← 目标是名义值 27.9 + 助推
目标 +36  实际 +62   +5.00A     ← 实际跳到名义值的 2.2 倍
目标 +41  实际 +23   +8.00A
目标 +31  实际 +52   +1.60A
```

**目标 27.9 RPM，实际在 0 ↔ 71 RPM 之间暴力来回冲，电流 7~11A。**

而外环自己只贡献几个 RPM。所以**直线精度的根因是驱动器速度环自己的极限环**，
这一层外环够不着 —— 外环只能改"要它转多快"，改不了"它内部怎么调"。

这也解释了 `chassis_check.py` 报的"全程 31% 而稳态 106%"：不是自相矛盾，是
速度在剧烈振荡，而"稳态"只取尾部 40%，恰好采到了波峰。

**能治它的只有两条路**（也就是本文档早先那句"要么找厂家调，要么在 STM32 上用
扭矩模式自己做速度环"）：
1. 找厂家调 / 关掉驱动器内部的速度环参数 —— 协议不暴露这些寄存器。
2. **STM32 切扭矩模式，自己做速度环。** FOC 的扭矩指令是平滑的，这样也不再有
   第二个环跟它打架。代价是安全性模型变了：**扭矩模式下"指令卡住"= 持续加速**
   （速度模式只是匀速跑），必须配电流限幅，并依赖 IWDG + 上电刹车帧兜底。

## 状态上报

STM32 每 50ms 往 USART1 发**两帧**：

| 帧 | 长度 | 内容 |
|---|---|---|
| 主遥测帧 `0x7B` | 24 字节 | 标准 Wheeltec 格式：车体 vx/vy/wz、IMU 六轴、电池电压 |
| 扩展诊断帧 `0x7E` | 36 字节 | 本工程自定义：**每路驱动器的最终命令/实际转速、输出电流、故障码、模式** |

帧顺序**不能反**：主遥测在前、诊断帧紧跟，诊断帧永远夹在两个 24 字节帧之间。

**为什么厂商节点不会被这一帧干扰**：它的入帧条件是「上一字节是帧尾 `0x7D`
（或 `0x7F`）、本字节是帧头 `0x7B`」。诊断帧自己的帧头是 `0x7E`、帧尾是 `0x7D`，
所以它会被整帧跳过，紧接着的那个 `0x7B` 恰好满足入帧条件 —— 24 字节帧一帧都不丢，
**厂商侧不需要任何改动**。

### 怎么读诊断帧

```bash
# 串口是独占的: 先把厂商底盘节点停掉 (Ctrl-C), 看完再起回来
python3 tools/decode_diag.py -p /dev/wheeltec_controller

# 只看有问题的轮子
python3 tools/decode_diag.py -p /dev/wheeltec_controller --only-problems
```

输出长这样：

```
seq=3   vx= +145 wz=   +0 | 1号 目标 +28 实际  +0  +0.02A 速度   正常   | 2号 目标 +28 实际 +28  +1.75A 速度   正常
    !! 1号 命令 +28 RPM 但实际 +0 RPM 且电流仅 0.02A -> 驱动器没给力(查故障码/使能/接线)
```

**输出电流是判断「这个轮子到底有没有劲」唯一的客观指标**，它把两种情况分开了：

| 现象 | 含义 |
|---|---|
| 目标有转速、实际不转、**电流≈0** | 驱动器根本没给力 → 查故障码 / 使能 / 接线 |
| 目标有转速、实际不转、**电流很大** | 给了力但被堵住或拖住 → 查机械卡滞 / 负载 |
| 目标有转速、实际也有、电流正常 | 正常 |

故障码表来自 `docs/foc-driver-protocol-v1.2.pdf` 第 11 页，脚本里已经内置：

```
0 正常   1 驱动器故障   5 过流   6 过压   7 欠压   8 过温
23/24 电机2/1 霍尔故障   25/26 电机2/1 堵转
27 UART 故障   28 RS485 故障   29 CAN 故障
```

> **7 = 欠压值得特别注意**：车上电池实测 26.6V 左右，而电机是 36V 额定的，
> 加速时电池一压降就可能触发欠压保护，表现正是「这个轮子突然没劲了」。

### 台架复验（轮子必须悬空）

串口是独占的，所以「下令」和「看数据」不能分成两个程序。`--drive` 让脚本
一边下发命令一边解码：

```bash
# 1. 停掉厂商底盘节点 (Ctrl-C)，否则串口抢不到
# 2. 轮子架空，按顺序跑这几条，每条都用 Ctrl-C 或 --seconds 结束
python3 tools/decode_diag.py -p /dev/wheeltec_controller --drive 0.10 0 --seconds 3
python3 tools/decode_diag.py -p /dev/wheeltec_controller --drive 0 0.30 --seconds 3
python3 tools/decode_diag.py -p /dev/wheeltec_controller --drive 0 -0.30 --seconds 3
```

看什么：

| 现象 | 结论 |
|---|---|
| 两个轮子都转、电流都是正数、方向对 | 正常，可以上地面 |
| 某一路 `实际` 始终 0 且 `故障` 非 0 | 驱动器报故障，按故障码查 |
| 某一路 `实际` 始终 0、`故障`=0、**电流≈0** | 驱动器没给力 → 先查驱动器使能、功率电、CAN 接线（**和继电器无关**，继电器只管滚刷/水泵）|
| 某一路 `实际` 始终 0、`故障`=0、**电流很大** | 给了力被堵住 → 查机械卡滞 |
| 原地转向时两轮 `目标` 一正一负 | **正常**，差速车原地转就是这样 |

脚本退出时会自动连发一串零速把车按住。STM32 另有 800ms 看门狗兜底。

## RK3588 侧的准备

> **完整说明见 [`docs/ros-integration.md`](docs/ros-integration.md)** —— 启动命令、
> 验证过的状态、车型配置、传感器安装位置怎么改、还缺什么，都在那里。
> 这里只留最关键的一条。

底盘通过 **CH340 (`1a86:7523`)** 接 RK3588 的 USB。厂家的 udev 规则只认
CP2102 (`10c4:ea60`) 和 CH343 (`1a86:55d4`)，**不认普通 CH340**，
所以要自己加一条（已经加在车上那台 RK3588 上了）：

```udev
# /etc/udev/rules.d/wheeltec_controller_ch340.rules
KERNEL=="ttyUSB*", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", \
  MODE:="0777", GROUP:="dialout", SYMLINK+="wheeltec_controller"
```

普通 CH340 **没有唯一序列号**（`ID_SERIAL=1a86_USB_Serial`），只能按 VID:PID 匹配。
以后要是加第二个 CH340，改成用 `KERNELS=="3-1.2"` 指定 USB 物理口。

生效后 `/dev/wheeltec_controller -> ttyUSB*`，厂商的 launch 文件不用改。

## 安全机制

| 机制 | 行为 |
|---|---|
| STM32 看门狗 | 上位机 800ms 不发命令 → 刹车 + 断开滚刷/水泵继电器 |
| 上电 | 先发刹车帧、继电器断开，车不会自己跑 |
| 命令限幅 | `MAX_LIN_SPEED` / `MAX_YAW_RATE` 夹住，上位机发疯也冲不出去 |
| 待机 | 每个控制周期重发同一帧刹车，**无状态**（见下） |
| 轮速外环修正 | 目标为 0 时恒定输出 0 —— 外环**无法**在停车指令下把车带着走；且总输出限在 ±`MAX_RPM` |
| 驱动器就绪联锁 | 两个驱动器没都回码时**只发刹车**，不发速度（差速车单轮出力 = 原地打转） |

### 继电器（PB0 滚刷 / PB1 水泵）—— 和轮毂电机无关

| | 上电 | 什么时候合闸 | 控制什么 |
|---|---|---|---|
| **滚刷继电器** PB0 | 断开 | **只能由上位机显式发 `f[1]=0x05` 帧** | 扫地滚刷电机 |
| **水泵继电器** PB1 | 断开 | **只能由上位机显式发 `f[1]=0x05` 帧** | 水泵 |

`f[2]` 是掩码：`bit0` 滚刷、`bit1` 水泵。

> ★ **这两个继电器是"外设开关"，和轮毂电机没有任何关系。**
> 轮毂电机的 FOC 驱动器是**独立供电、常电**的 —— 继电器断开不给它们断电，
> 它们的 CAN 通信和使能状态都不受影响。
>
> 这条以前写错了（PB0 叫 `RELAY_MOTOR` / "电机继电器"，还写成"继电器给驱动器
> 供电"），结果所有基于"继电器合闸 = 驱动器上电初始化"的推理全是错的，白追了
> 一轮"为什么第一条命令没反应"。**名字已经全改成滚刷**，别再叫电机。

**滚刷曾经是"收到运动命令就自动合闸"**，但那个行为的理由（"不合闸电机就没电"）
本身就是错的 —— 那个"电机"指的是轮毂驱动电机，继电器根本不管它。于是它成了一个
**没人明确决定过的副作用**：一给运动命令扫地滚刷就转。**已按需求改成显式控制。**

**★ 两条看门狗必须分清**（以前混成一条，导致显式控制根本没法用）：

| | 判据 | 动作 |
|---|---|---|
| **运动看门狗** | 800ms 没收到**速度帧** | `target` 归零 + 刹车 |
| **链路看门狗** | 800ms 没收到**任何合法帧** | 断开两个继电器 |

分开的理由：只发继电器帧时，车必须停住（没有速度命令），但滚刷要保持转 ——
混成一条的话，继电器帧不算喂狗，"开滚刷"会在 800ms 后自己被断链保护关掉。

**怎么控制它们**：

```bash
# 台架: 直接开关 (需要先停掉 ROS 底盘节点, 串口独占)
python3 tools/decode_diag.py -p /dev/wheeltec_controller --relay 1   # 滚刷开
python3 tools/decode_diag.py -p /dev/wheeltec_controller --relay 2   # 水泵开
python3 tools/decode_diag.py -p /dev/wheeltec_controller --relay 3   # 都开
# Ctrl-C 退出时会自动发 0 关掉
```

> ⚠ **ROS 栈跑着的时候目前开不了滚刷。** 这条 `f[1]=0x05` 是本工程自定义的扩展，
> 厂商 `wheeltec_robot_node` 不认识它，而它**独占串口**。所以要在 ROS 里控制滚刷，
> 必须给厂商节点加一条转发通路（订阅一个话题 → 组这条 11 字节帧发出去）。
> 见 `docs/ros-integration.md` 的缺口表。

## 已知的坑（都踩过）

- **继电器模块必须和 STM32 共电源共地**，否则光耦半开、线圈半通电、持续嗡嗡响
- **STM32F1 的 USART 没有 RX FIFO**，收包必须用中断 + 环形缓冲，轮询一定会丢字节
- **CAN 收发器和 STM32 之间选对电平**，PA11/PA12 不是 5V 容忍
- **Blue Pill 的 PA11/PA12 同时连着 USB 座**，用 CAN 时别插那种会短接 D+/D- 的充电器
- **不要用「位置模式锁位」实现待机时锁死轮子**（重要，已踩）。做法是先刹停、
  再切 `MODE_POSITION`、然后每个周期死守驱动器回码里的位置。它在台架上表现很好
  （推一下会弹回原位），但**实车上直接失控**：驱动器被切出速度模式后，靠一路
  陈旧的绝对位置目标维持，多出「模式切换」和「位置目标」两个变量。
  现已删除，停车路径是**无状态**的——每个控制周期重发同一条帧，不记忆、不切换。
  想调待机手感只改 `main.c` 里的 `STOP_CTRL` 一个宏（`CTRL_BRAKE` 动态制动 /
  `CTRL_DISABLE` 自由滑行 / `CTRL_ENABLE`+0）。实测 `CTRL_BRAKE` 在低速时制动力
  很弱，慢慢推仍能推动——这是这台驱动器的固有特性，用锁位去换它的代价不值得。
- **原地转向时两个轮子反向转是正常的**，不是故障。左轮 `vx - wz·b/2`、右轮
  `vx + wz·b/2`，原地转（`vx=0`）时两轮等速反向。看到「内轮倒转」别急着断电。
- **串口是独占的**：厂商 ROS 节点开着的时候，`decode_diag.py` 打不开同一个口。
  看诊断数据必须先停节点。
- **改诊断帧长度时三处要同步**：`main.c` 的 `DIAG_FRAME_SIZE`、
  文件头的布局注释、`tools/decode_diag.py` 里的 `DIAG_SIZE`。对不上会静默丢帧。
- **给 YbImu 读长块会把模块卡死**（重要，已踩）。为了查"陀螺仪为什么恒 0"，
  加了一个寄存器体检去读 `0x16`（四元数，**16 字节**）和 `0x26`（欧拉角，12 字节）。
  结果 IMU 诊断码从 `陀螺仪恒 0` 直接变成 `总线死`（起始条件拉不起来），
  **连本来正常的加速度都读不到了，而且一直不恢复** —— 为了诊断把器件搞死，
  比不做体检还糟。现在体检只读 3/6/6 字节这些短块
  （`0x01` 版本 / `0x0A` 陀螺 / `0x10` 磁力）。
 真要再试长块，得先确认那颗模块上确实存在这些寄存器 —— 头文件那份表可能
  抄自另一个批次的变种（本车读到 `ver=1`）。
- **I2C 驱动的错误路径必须发 STOP**。同一个坑暴露出的底层缺陷：`YbImu_ReadRegs()`
  有几条错误分支 `return` 前没发 STOP，从机会一直拉着 SDA 不放，**整条总线
  卡死到断电为止**。已全部补上，并加了标准总线恢复（空闲时发现 SDA 被拉住就
  补 9 个 SCL 脉冲让从机松手）。任何 I2C 驱动都该有这个。
- **不要用"读一遍所有寄存器"来判断模块死活之后就把结论写死**。体检标志位里
  "没读到"和"读到了但是 0"是两回事，显示时不能混为一谈，否则会把人带偏。
- **"监控工具本身也会成为故障源"**（重要，已踩）。第一版底盘看门狗每 10 秒新建一个
  ROS 节点、只转 4 秒就判 `/odom` 死活，而**新建节点的 DDS 发现本身可能就要好几秒**
  —— 于是它在**完全健康的栈上反复误判重启**，日志里实打实重启了 3 次。每次重启
  `/odom` 位姿归零，正在进行的测量被截断，现象是"车明明动了、里程计只涨一点点"，
  而且**完全不可复现**，为此白追了好几轮。现在改成：进程没了才立即重启（不依赖
  DDS）；数据探测要**连续失败 3 次（30 秒）**才动手。另外 `pgrep -f` 的模式要带前导
  斜杠（`/wheeltec_robot_node`），否则它会匹配到任何命令行里含这串字的进程 —— 实测
  匹配到了自己那条 `pgrep` 命令，于是节点真死了也可能被判成"还活着"。
- **"诊断脚本僵住不退"会悄悄毁掉后面所有测量**（重要，已踩）。`decode_diag.py`
  在读线程报 `SerialException` 之后，卡在 `halt()` 里那个**没有超时的 `write()`**
  上（CH340 在 USB 层掉线后 write 会阻塞）—— 进程**僵了 19 分钟不退出、还一直
  开着串口**；同一时期的 `turn_sweep.sh` 也没退。之后所有测量都是在"两个进程读
  同一个 tty"的状态下做的：字节被随机分走、丢帧，数据全废，而且**极难察觉**
  （现象只是"数字有点怪"）。已修三处：
  1. `serial.Serial(..., write_timeout=0.3)`，`write` 不再可能无限阻塞；
  2. 三个工具结尾都加 `os._exit(0)`，不给"优雅关闭卡住"留任何机会；
  3. `turn_truth.py` / `chassis_check.py` 启动后**自检 `/cmd_vel` 的发布者数**，
     发现除自己以外还有人在发速度就拒绝测量，并打印怎么查。
  **诊断工具的底线：宁可难看地强退，也绝不能僵在那里占着串口。**
- **`pgrep -f` / `pkill -f` 会匹配到"任何"命令行里含这串字的进程 —— 包括你自己。**
  这个陷阱栽过三次：看门狗的 `wheeltec_robot_node` 匹配到自己；我在 ssh 里敲
  `pgrep -c -f '/wheeltec_robot_node'` 把自己数了进去，误判"有两份栈"；
  `pkill -9 -f 'turn_sweep.sh'` 更是直接把自己那条 ssh 命令行杀了、命令当场中断。
  写这类判据时：模式里带路径前缀，**或者干脆用 `ps -eo pid,cmd | grep xxx |
  grep -v grep`** 再数。
- **看门狗会和台架调试抢串口，必须先暂停它。** `decode_diag.py --drive` 要求先
  停掉 ROS 节点（串口独占），而看门狗把"节点进程没了"当成故障、每 10 秒把栈拉
  回来抢串口 —— 实测连着重启了 4 次，`decode_diag` 最后报
  `multiple access on port?`，数据是废的。现在支持手动暂停：
  ```bash
  touch /tmp/chassis_watchdog.pause    # 调试前
  rm    /tmp/chassis_watchdog.pause    # 调完一定要删!
  ```
- **栈的完整性要查两个进程，不能只看 node。** 实测 `pkill` 掉 `ros2 launch` 之后
  `wheeltec_robot_node` 还活着，只查 node 就会认为"一切正常"—— 但这时 respawn
  已经不工作了。看门狗现在两个都查。
- **"同一条直行命令连发三次，结果分别是没反应 / 向左转 / 正常前进"**（重要，已踩，**根因未定**）。
  直行变左转只有一个解释：**那一次只有一个轮子出力** —— 差速车单轮出力就是原地打转。
  现在的对策是**驱动器就绪联锁** `Drive_Ready()`：两个驱动器没**各自回过码**、
  或者有一路**现在不回码**（超过 `RPM_STALE_MS`），就**只发刹车、不发速度**。
  这样单轮驱动的情况会被直接刹住，而不是变成一次歪着走。
  诊断帧 flags 新增 **bit5**，`decode_diag` 会打印 `驱动器未就绪(等回码, 车被刹住)`。
  > ⚠ 我一度把根因归到"继电器断了给驱动器断电、驱动器在重新上电初始化"——
  > **那是错的**，继电器管的是滚刷和水泵，和轮毂驱动器无关（驱动器常电）。
  > 等待条件本身仍然是对的，错的只是理由，所以联锁保留、理由重写。
  > **真正的根因还没查明**：需要抓到一次"失败那趟"的逐帧数据才能定性 ——
  > 看两个轮的 `目标` 是不是就已经不一样（STM32/上位机侧），
  > 还是 `目标` 一样而 `实际` 只有一个在动（驱动器/静摩擦侧）。
- **不能用"指令 vs 里程计"来验证里程计是否说真话**（重要，已踩）。`/odom` 的角速度
  就是 STM32 按轮速算出来的值、厂商节点直接取用，**它和指令同源，比值恒等于 1**，
  什么都验证不了。要验证只能找**独立的物理量**：IMU 陀螺仪、激光雷达，或者卷尺。
- **`systemctl restart` 会杀掉服务 cgroup 里的所有进程**。看门狗用 `nohup` 拉起的
  底盘栈属于它那个 service 的 cgroup，默认 `KillMode=control-group` 下
  `systemctl restart chassis-watchdog` 会把**正在正常工作的底盘连坐干掉**（实测
  踩到：停掉看门狗之后 `/odom` 立刻没了，一开始还以为是别的原因）。service 里已加
  `KillMode=process`。底盘该由 `chassis_bringup.sh` 管，不该被看门狗的启停连坐。

### IMU 陀螺仪"恒零"？—— 假故障，已撤销

**曾经的结论**：加速度正常、磁力计正常，只有陀螺仪三个轴全是字面 0，于是判定
陀螺仪坏了。

**实际是错的。** 当时的判据来自一个**没有依据的假设**——"真实陀螺仪静止也有
噪声"。实测结论正相反：**这颗模块在检测到静止时会把角速度输出直接置零**。
静止时 478/799 帧为 0，一旦转动就有 321 帧非零。所以"静止时读到 0"是它的
正常行为，不是故障。

**怎么判断陀螺仪死活**：只能靠"转一下看数值变不变"，**不能靠静止读数**。
固件里 `imu_gyro_ok` 现在的含义是"曾经读到过非零角速度"。

顺带把**符号**也验证了：原地左转（俯视逆时针）时 `/imu/data_raw` 的
`angular_velocity.z` 为**正**、右转为负，所以 `IMU_GYRO_Z_SIGN 1` 是对的。

**对 ROS 的影响**：厂商 EKF 确实在用它 —— `/imu/data_raw` 的
`angular_velocity_covariance[8] = 2.5e-3`（标准差 0.05 rad/s），是转动的主要
信息源；实测 `/odom_combined` 的偏航角和 IMU 几乎重合（73% vs 74%）。
（曾经以为"EKF 把它协方差设成 1e6 所以根本没在用"，那是把 **orientation** 的
1e6 当成了 angular_velocity。）

**遗留的真实缺口**：EKF 目前**没有任何绝对偏航参照**（没融合磁力计、也没雷达），
所以航向长期会漂。这个要等雷达装上、跑起 SLAM 才能治本。
