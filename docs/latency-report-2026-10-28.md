# `/cmd_vel` → 轮子实际转动 链路延迟实测报告

- 日期：**2026-10-28 09:35~09:36**（主机时间）
- 主机：**RK3576 / 192.168.5.11**（`smart`），ROS humble，`ROS_DOMAIN_ID=7`
- 路径：`/cmd_vel` → 厂商 `wheeltec_robot_node`（`base_serial.launch.py`）→ 串口 `/dev/wheeltec_controller` 115200 → STM32F103 → CAN 1 Mbps → 达妙 DM-H65 速度环
- 观测：`/odom`（20 Hz，`header.stamp` = 节点发布时刻）
- 条件：**车落地**、方向自检 `forward`、20 个阶跃 trial（±0.20 m/s，保持 0.6 s，方向交替）
- 代码：`tools/latency/`（`probe_latency.py` / `run_latency.sh` / `writets.c` / `analyze_latency.py` / `analyze_profile.py` / `selftest_analyze.py`）
- 原始数据：`tools/latency/results/latency_20261028_0936.json`、`writets_20261028_0936.log`、`profile_20261028_0936.txt`

## 1. 一句话结论

**从上位机发布一条 `/cmd_vel`，到轮子真的开始转，约 47 ms（保守 28~68 ms）。**
其中 **~21.6 ms 是纯上位机软件延迟**（厂商节点 20 Hz 阻塞大循环把 ROS 回调卡在网格上），
**~26 ms 是固件控制周期 + CAN + 驱动器 + 机械**。

停车反向看：**发 0 之后要 ~190 ms 才真正停住**（减速是斜坡，不是立即停）。

## 2. 分段结果

### T1 = 发布 → 节点把 11 B 命令帧写到串口（µs 级精确）

| 统计 | 全部（64 条） | 仅阶跃（20 条） |
|---|---|---|
| n | 64 | 20 |
| min | 0.6 ms | 0.6 ms |
| p25 | 4.1 ms | 4.1 ms |
| **p50（中位）** | **21.9 ms** | **21.6 ms** |
| p75 | 31.4 ms | 29.2 ms |
| p95 | 40.4 ms | 38.7 ms |
| max | 43.3 ms | 38.9 ms |
| mean | 19.9 ms | 19.3 ms |
| 落在 0~50 ms | **64/64 = 100 %** | 20/20 |

5 ms 直方图（0→50 ms）：`17 4 4 6 6 9 6 7 5 0`

**跨 trial 呈锯齿**：T1 依次为 38.7 → 33.9 → 29.2 → 23.7 → 18.2 → 11.5 → 4.1 → 0.6 → 0.7 → 33.7 → 25.8 → 19.6 → 11.9 → 4.9 → 0.6 → 0.7 → 38.9 → 33.6 → 27.5 → 28.3 ms。
每 trial 相位漂移约 4.5~6 ms 后复位——因为 trial 周期 1.8045 s 不是 50 ms 的整数倍，
而发布只能落在 20 Hz 网格上。**这是"回调被 20 Hz 循环量化"的硬证据。**

### T2 = 串口写出 → 轮子真的开始转（只能给区间）

| 证据 | τ |
|---|---|
| 最后一个"明确没动"的采样 | **5.8 ms**（12 个样本，v = +0.000） |
| 第一个"明确在动"的采样 | **45.8 ms**（3 个样本，v = +0.056 m/s） |
| 线性外推过零（假设恒定加速度） | ~1~10 ms（**不可信**，见下） |
| 物理预算 | USB ~2 + STM32 `CTRL_PERIOD_MS=20`（0~20）+ 驱动/机械 ~10 ≈ **12~32 ms** |

**T2 取 ~26 ms（区间 6~46 ms 的中点）。**

> **为什么不能更准**：厂商节点每轮循环是「等 24 B 遥测 → 发 `/odom` → `spin_some` → 写串口」，
> 所以"写串口"永远紧跟一次 `/odom` 发布（实测 τ≈0~6 ms 就有一帧）。
> 观测网格和命令网格被锁在一起，τ ∈ (6, 40) ms 窗口**没有任何样本**，
> 50 ms 量化**无法靠多点统计消除**。要定死 T2 只能提高遥测上报率（改固件，本次不允许）。

### T_total = 发布 → 轮子开始转

**T1 21.6 + T2 26 = ≈ 47 ms**；保守区间 **28 ~ 68 ms**（=21.6+6 ~ 21.6+46）。

### T_stop = 发 0 → 真正停住

从减速曲线看：发 0 后 τ=3.4 ms 仍在上一个平台 0.185 m/s，**约 26 ms 后开始降**，
然后 0.135 (48 ms) → 0.082 (98 ms) → 0.031 (148 ms) → **≈0 (193 ms)**。
即**减速段约 150~190 ms**，斜率约 1 m/s²。之后还有 +0.02~−0.04 m/s 的过零抖动（约 ±20 mm/s，疑似编码器过零/机械回差）。

## 3. 顺带测到的响应形状（`analyze_profile.py` 合并重建）

把 20 个 trial 的 (τ, v) 汇总分箱，重建出阶跃响应 v(τ)（τ 从串口写出算起）：

| τ (ms) | 0~6 | 46 | 101 | 151 | 201 | **241** | 301 | 351 | 401 | **451** | 501 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| v (m/s) | 0.000 | 0.056 | 0.123 | 0.172 | 0.203 | **0.252** | 0.233 | 0.233 | 0.209 | **0.185** | 0.187 |

- 命令 0.20 m/s → 响应**上升约 250 ms**，然后**过冲 +26 %**（0.252 @ 241 ms），
  再回落到 **0.18~0.19（−9 %）**并稳定 → 典型的欠阻尼速度环（`KP_ASR`/`KI_ASR` 偏大、`ACC/DEC` 偏小）。
- 也就是：**短脉冲（≤0.6 s）里车实际跑的速度会先高 26 %、后低 9 %**，
  平均比命令值高 5~10 %。对"我让它转多快它就转多快"这类需求，这段约 0.5 s 的瞬态是可感知的。
- 观测链路自身开销极小：`/odom` 到达本机比 `header.stamp` 晚 **2.2 ms（p25~p95 1.9~2.9）**，可忽略。
- 静止噪声：`vwheel` 最大 **0.0011 m/s**（`vx` 恰好 0.0000），所以动/不动的判据门限 0.010 m/s 很安全。

## 4. 值得做的优化（按性价比）

1. **改掉厂商节点的大循环**（收益 ≈ 20 ms，占 T_total 的 43 %）：
   用 `MultiThreadedExecutor`，或单独起一个线程只做 `spin` 收 `cmd_vel` + 写串口，
   主循环只管收遥测/发 odom。**行为不变，纯调度改造。**
2. **提高遥测上报率**（把 T2 从"区间"变成"数值"）：固件把 24 B 帧从 20 Hz 提到
   50~100 Hz（115200 波特率下 24 B×100 Hz = 24 kB/s，够用），才能把 T2 定到 ±5 ms。
3. **调驱动器速度环**削弱过冲：先把 `KP_ASR` 调小 / 加大 `ACC/DEC` 斜坡，
   把 0.5 s 瞬态压下去——这直接影响"跑得准不准"。
4. 若最终要"发一条命令就停"，注意**停车还有 ~190 ms** 的斜坡尾，
   上层做轨迹时要预留（或在固件里把 DEC 设得更陡）。
