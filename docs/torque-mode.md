# 力矩模式实验（`torque-mode` 分支）

> **这条分支的目的**：把驱动器内部那个**有极限环的速度环**整个换掉 —— 改由 STM32
> 发**扭矩**（模式 `0x04`）、自己做速度环。
>
> **这不是可以顺手合回 `main` 的东西**，是一份实验。`main` 上跑的还是速度模式。

---

## 1. 为什么要试这个

实测（`docs/nav2-reference.md` §…）：**目标 27.9 RPM，驱动器回码的实际转速在
0 ↔ 71 RPM 之间暴力来回冲，电流 7~11 A。** 而我们的外环（`Trim_Apply`）在这件事上
只能贡献几个 RPM —— 它改得了"要它转多快"，改不了"它内部怎么调"。

能治它的只有两条路，而这个分支是第 2 条：

| 路 | 状态 |
|---|---|
| ① 找厂家调驱动器内部的速度环参数 | **协议不暴露任何参数读写**（CAN/串口/BLE 都没有，`docs/foc-can-protocol.md` §6 已用厂家资料核实）→ 我们调不了，只能找厂家 |
| ② **STM32 切扭矩模式，自己做速度环** | ★ 本分支 |

支撑第 ② 条的关键事实（2026-10-11 才确认）：**扭矩模式 `0x04` 确实存在** ——
单位 A、量程 ±10.0 A、写入值 = **电流 × 10**。我们以前判断"`0x04` 不存在"是**错的**，
详见 `docs/foc-can-protocol.md` §2.1 / §7。

## 2. 怎么编译烧录

**这个分支上，`DRIVE_MODE_SEL` 的默认值就是 `DRIVE_MODE_TORQUE`。**
所以**照常选 target 就行，不需要额外选 target、更不需要手改源码**：

1. Keil 打开 `firmware/stm32-chassis/stm32-chassis.uvprojx`
2. target 选 **`sweeper`**（或 `scrubber`）
3. **`F7` 编译**（换 target 后必须编译，不能直接 F8 —— 见 README 里那次"烧错固件"事故）
4. `F8` Download
5. **两级复核**：
   - **看灯**：2 Hz = 扫地机，5 Hz = 洗地机
   - **看数据**：`python tools/decode_diag.py -p <串口>` → 行尾应出现
     **`★力矩模式固件`**（诊断帧 `[26]` bit2，只有力矩模式固件才置位）

想在本分支上编**速度模式**做 A/B：命令行加 `-DDRIVE_MODE_SEL=0`，或把
`main.c` 里那个默认值改回 `DRIVE_MODE_SPEED`。

> ★ **本分支上「上电自检点动」默认是关的**（`SELFTEST_ENABLE` 在力矩模式下为 0）。
> 理由：自检会在上电 3 秒后自己往前窜一下，而力矩模式的增益**全是没标定的估计值**，
> 同一条命令可能窜出去很远。台架标定完、确认过幅度之后再手动开回 1。

## 3. 安全壳（这是本分支最该看懂的部分）

**速度模式：指令卡住 = 匀速跑（危险但收敛）。
扭矩模式：指令卡住 = 持续加速（不收敛）。** 所以这里多了一整套东西：

### 3.1 控制律

```
误差 = 目标轮速 - 实际轮速
P    = TQ_KP × 误差
I   += TQ_KI × 误差 × dt          （带抗饱和，积分自己不许超过 ±TQ_MAX_A10）
起步力矩下限：轮子还没转起来时，输出至少给到 tq_floor
硬限流：|输出| ≤ TQ_MAX_A10
变化率限幅：每周期最多变 TQ_SLEW_A10_PER_S × dt
```

**为什么需要"起步力矩下限"**：速度模式下静摩擦是**驱动器**帮忙顶过去的（它的环会
一直加电压直到轮子转）。扭矩模式下没有这个东西了 —— 纯 PI 要等积分自己爬到起步
力矩，起步会很慢，而且极低速会"给一下就停、停一下再给"地抖。

**★ 这个下限会自己往上爬**（`TQ_FLOOR_*`）：从 0.8 A 起，只要"有目标却没转起来"
就每 250 ms 加 0.4 A，一直爬到 `TQ_MAX_A10` 为止；一转起来立刻收回起始值。
理由是**我们不知道这台车起步要多少扭矩**（静摩擦/载重/坡道都影响）：
- 固定成小值 → 扭矩不够 → 不转 → 被误读成"力矩模式不工作"
- 固定成大值 → 起步窜

爬升过程**能从驱动器回码的电流栏直接看到**，所以顺手就把"起步需要多少电流"量出来了。

**★ 两轮共享一个下限**（不是每轮各爬）：和当初助推同样的理由 —— 各自爬升会让两轮
指令差出十几，起步时车会歪一下。

### 3.2 三道保护（`Torque_Guard`）

| # | 判据 | 挡的是什么 |
|---|---|---|
| 1 | `\|实际\| > 60 RPM`（`TQ_ABS_MAX_RPM`）→ **立刻锁存** | 绝对失控 |
| 2 | `\|实际\| > \|目标\| + 25 RPM` 持续 800 ms → 锁存 | 环不稳定 / **接线反了**（接线反了闭环就变成正反馈，实际转速会朝反方向越来越大，一定撞上这条）|
| 3 | 有目标、轮子不转，**且下限已爬到 `TQ_MAX_A10`** 后再持续 2 s → 锁存 | 真卡住 / 驱动器根本不认 `mode 4`（那就是白给电流发热）/ 轮子被顶住 |

**第 3 条为什么带"下限已爬满"这个条件**：只看"两秒没转"会把**起步电流不够**误判成
堵转，而那是调参问题、不是故障。

**两轮一起判、一起停** —— 单轮自己收手会让差速车原地打转，而"打转"比"停下"危险。

### 3.3 锁存的解除

锁存后**只发刹车帧**（车表现为"不走"），直到**目标为 0 且持续 500 ms** 才允许重新起步。

- 为什么不停到断电：机器人不能因为一次保护就得人工重启
- 为什么不立刻自动重试：那样就成了"抖一下停一下"的循环，比停着更难看也更危险

**诊断帧 `[26]` bit3 = 1 就是"扭矩保护已锁存"**，`decode_diag.py` 会印出来。

### 3.4 停车 / 待机

- **目标为 0（两个轮都是）→ 发 `mode 4` + `CTRL_BRAKE` + 0**，即动态制动。
  用刹车而不是"0 扭矩" —— **0 扭矩 = 自由滑行，那不是停车**。
- 全固件所有停车路径（上电、800 ms 看门狗、驱动器未就绪、保护锁存）都自动跟着
  驱动模式走，因为 `CAN1_SendStop` 是按模式定义的。
- **模式号恒定不变**：一旦是力矩模式就一直发 `mode 4`，绝不"跑着跑着切模式"
  （协议要求"模式切换需在电机停止空闲状态下生效"，`docs/foc-can-protocol.md` §2.3）。
- 单个轮目标为 0（原地转时的内轮）→ 那一轮**发刹车**，而不是 0 扭矩。动态制动是被动
  的、不注入能量，手感也更接近速度模式下"内轮被按在 0"。

## 4. 台架测试步骤

> ⚠ **第一步必须架空（驱动轮离地）**。原因：`TQ_KP/TQ_KI/TQ_STICTION` **全是没标定
> 的估计值**，而且扭矩模式下参数不对的后果是"持续加速"，不是"匀速跑"。

### 第 1 步：架空，确认驱动器和方向

```bash
# 串口要独占: 先停厂商 ROS 节点
python tools/decode_diag.py -p /dev/wheeltec_controller --drive 0.05 0
```

- `--drive 0.05 0` = 前进 0.05 m/s。洗地机折算约 **6 RPM**、扫地机约 **5 RPM** ——
  **远低于**速度模式实测的起步门槛（约 15 RPM）。
- **在速度模式下这个小命令会让车愣在原地不动**（那正是"小转向命令没反应"的成因）；
  **在力矩模式下它应该能动** —— 这就是本实验要看的第一个结论。

看什么：

| 现象 | 含义 |
|---|---|
| 轮子**缓慢、平稳**地转 | ✅ 假设成立：扭矩模式+我们的环能做出速度环做不到的低速 |
| **一冲一停**地转 | 增益不对（`TQ_KP` 太大或 `TQ_KI` 太小），先调这两个 |
| **完全不动**，且**电流栏有值在涨** | 起步力矩在爬但还没到位 → 是电流不够，等它爬到 / 调大 `TQ_MAX_A10` |
| 完全不动，**电流栏一直 0** | 环没在给 → 看 flags bit6（"扭矩出力中"）亮不亮；不亮查 `目标` 有没有传下来 |
| 不动，且行尾出现 **`扭矩保护已锁存`** | 下限爬满仍不转 → 真堵转/驱动器不认 `mode 4` |
| **两个轮子方向相反 / 车原地打转** | 接线方向标定不对（`MOTOR1_IS_LEFT`/`INVERT`）→ 先回去验接线 |
| 转速**越来越快收不住** | 立刻断电，然后看是不是撞了保护(1) |

### 第 2 步：落地，测低速直线

```bash
python tools/decode_diag.py -p /dev/wheeltec_controller --drive 0.10 0
python tools/decode_diag.py -p /dev/wheeltec_controller --drive 0.20 0
```

重点是**对比速度模式下的同一个命令**。速度模式下 0.20 m/s 附近会看到
`实际` 在 0 和目标之间暴冲、电流 7~11 A；力矩模式如果做对了，`实际` 应该明显更平滑。

**先小步**：`0.10` → `0.20` → 再往上。

### 第 3 步：只在这两步都过了之后

- 才考虑把 `TQ_MAX_A10` 往上放（爬坡/载重要求更大电流时）
- 才考虑把 `SELFTEST_ENABLE` 开回来
- 才考虑原地转 / 高速 / 长时间跑

## 5. 参数表（都在 `main.c` 的"力矩模式参数"那一段）

| 宏 | 默认 | 含义 | 怎么调 |
|---|---|---|---|
| `TQ_KP` | `1.2f` | A×10 / RPM | 响应太慢→加；抖/冲→减 |
| `TQ_KI` | `0.6f` | A×10 / (RPM·s) | 稳态差 → 加；低频晃 → 减 |
| `TQ_MAX_A10` | `30.0f` | **硬限流** = 3.0 A | 不动就往上放，**绝不超过 100(=10 A)** |
| `TQ_STICTION_A10` | `8.0f` | 起步下限**起始值** = 0.8 A | 一般不用改，它会自己爬 |
| `TQ_FLOOR_STEP_A10` / `_MS` | `4.0f` / `250` | 下限爬升速度 | 想快点找到起步电流→调小 `_MS` |
| `TQ_SLEW_A10_PER_S` | `120.0f` | 指令变化率上限 | 起步太冲→减 |
| `TQ_DEADBAND_RPM` | `2.0f` | 误差死区 | 原地抖→加 |
| `TQ_RUNAWAY_MARGIN_RPM` | `25.0f` | 超目标多少算可疑 | 正常减速都误报→加 |
| `TQ_ABS_MAX_RPM` | `60.0f` | 绝对上限 | 只该往下调，不该往上 |
| `TQ_STALL_MS` | `2000` | 下限爬满后仍不转多久算堵转 | 给调试留时间→加 |

> ⚠ **这些数全是"量级上说得通"的估计，不是实测值。** 唯一已知的锚点是
> 满量程 ±10.0 A，以及速度模式测出的"起步门槛约 15 RPM"（那是电压域的量，换算不成
> 电流，只能当提醒：静摩擦不小）。**标定结果请记回本文档。**

## 6. 已知差异 / 本版**没做**的事

- **没有"停车保持力"**。目标为 0 时仍然是 `CTRL_BRAKE` 动态制动 ——
  待机时**没有保持力**（静止时制动力 ≈ 0，这是这台车"发 0 停不住"的根因）。
  扭矩模式**理论上**能做保持（给一个恒定扭矩顶住，或做位置闭环），但那是另一步，
  本版故意不做：没有位置反馈的恒定扭矩只会把车推着走，不是保持。
- 目标为 0 的**单轮**发刹车（不是 0 扭矩），见 §3.4。
- **诊断帧没有"扭矩指令"这一栏**。力矩模式下"目标"栏报的是**名义目标轮速**（不是
  扭矩），想看在给多少扭矩请**看驱动器回码的电流栏**（力矩模式下它 ≈ 我们的指令）。
  台架判据主要靠三样：`目标 vs 实际`、`电流`、`flags bit6`。
- 实验分支，**别合回 `main`**（至少别在标定之前）。

## 8. 记录（标定结果填这里）

### 2026-10-12 洗地机 · 第一次台架实测（`TQ_MAX_A10 = 30`，即 3 A）

命令 `--drive 0.05 0`（0.05 m/s ≈ 6.4 RPM/轮），2 秒。洗地机固件：`洗地机150/425` + 力矩模式。

**✅ 扭矩链路整条是通的（这是本次最有价值的结论）：**

| 观测 | 含义 |
|---|---|
| 驱动器回码 `模式 = 力矩` | **驱动器确实吃下了 mode 4** —— 第一次实证 |
| 电流跟着我们爬升的逻辑走（0.1 → 2.5 A）| 我们的扭矩指令**真的到了电机** |
| `fl=…起步助推中/扭矩出力中` | 扭矩环在出力 |
| `can_err=0 坏帧=0 溢出=0 故障正常` | 通信链路干净 |

**❌ 但车完全没动：**

| 观测 | 值 |
|---|---|
| `实际` 转速 | 全程几乎 +0（2 号闪过两次 +10）|
| IMU 加速度峰峰值 | x=0.01 y=0.01 z=0.03 m/s² —— **独立裁判：车一点没窜** |
| 电流上限 | 2.5 A（限流 3.0 A）|

**故障定位：限流太低。** 依据不是猜 —— **扫地机在速度模式下正常行驶时，
驱动器回码的电流是 7~11 A**。也就是说推这台车本来就需要这个量级的电流，
3 A 只有它的 30%。用户当时在场，确认：**轮子自由的、手能推动**（排除了机械刹车）。

**⚠ 一个还没排除的并列原因**：`MOTOR2_INVERT` 是照抄扫地机的，**洗地机上从没验证过**。
本次数据里 1 号电流为正、2 号电流为负（目标都是 +6），且 2 号在被命令负电流时实际
转速冒出 +10 —— 有"两轮对顶"的嫌疑。**所以下一次测试先做原地转（pivot）而不是直接
前进**：pivot 命令在两种情况下都是轮子"彼此一致"的（flag 对 → 原地转；flag 错 →
整车平移），**不会出现两轮互相较劲**，而且用 IMU 的陀螺仪就能分辨是"转了"还是"平移了"。

**参数改动（本次）：**

| 宏 | 原值 | 新值 | 依据 |
|---|---|---|---|
| `TQ_MAX_A10` | 30 (3 A) | **80 (8 A)** | 扫地机正常行驶 7~11 A；8 A 仍在驱动器满量程 10 A 内 |
| `TQ_STICTION_A10` | 8 (0.8 A) | **25 (2.5 A)** | 起点离起步门槛太远（爬到 3 A 都没动）|
| `TQ_FLOOR_STEP_A10` | 4 (0.4 A) | **10 (1 A)** | 爬升太慢，台架一轮看不到起步那一刻 |
| `TQ_FLOOR_STEP_MS` | 250 | **200** | 同上 |
| `TQ_STALL_MS` | 2000 | **3000** | 给"起步力矩够不够"留观察窗口 |
