# pos-mode 分支：位置模式实验

> **这不是 main。** 这是为了回答一个问题而做的实验分支：
> **换成位置模式，轮子会不会走得更准？**
>
> 起因：驱动器内部那个速度环欠阻尼 —— 阶跃下去过冲到 **138%**（实测）、约 3 秒才
> 落回，而且协议不暴露它的 PID。位置环是另一套：位置误差小到 0.1° 也会出力，
> 没有速度环那种"误差小就没劲"的死区，所以**低速和定位理论上会更准**。

## ⚠ 这个方向有前科，必须知道

`main` 的 README 里有一条踩坑记录：**"不要用「位置模式锁位」实现待机时锁死轮子"**，
做法是「先刹停 → 再切 `MODE_POSITION` → 然后每个周期死守驱动器回码里的位置」，
台架上表现很好（推一下会弹回原位），但**实车上直接失控**。

当时归因是：驱动器被切出速度模式后，**靠一路陈旧的绝对位置目标维持**，平白多出
「模式切换」和「位置目标」两个变量。

**所以这一版和那一版的区别，必须说清楚**（否则就是把同一个坑再踩一遍）：

| | 上次（失控） | 这一版 |
|---|---|---|
| 位置目标的来源 | 我们自己的累加器，**一进位置模式就命令它** | **第一帧用驱动器实测位置播种**（`pos_t = m_pos`） |
| 模式 | 走/停之间**反复切模式** | **只进不出**，停车 = 保持当前位置 |
| 绝对角离实际多远 | 未知，可能很远 → 最大电流冲过去 | **恒为 0**（播种），之后只领先一个跟随误差 |
| 跟随误差 | 没有限制 | **限幅 ±90°**，轮子被堵住时目标不许跑掉 |
| 角回绕 | 没处理 | `WrapDeg` / `WrapDiff` 折回 ±32768° 再比较 |

**"播种"这一行是这一版敢做的全部理由** —— 它从机制上消掉了上次那条路径。

## 改了什么

### 固件（`firmware/stm32-chassis/user/main.c`）

1. **读位置回码**：以前只解析到 `DATA5`，**`DATA6/7`（当前位置，度）从来没读过**。
   现在按 `DLC>=8` 解析，并置 `pos_seen_mask` 位。
2. **位置模式下发**（`DRIVE_MODE_POSITION 1`）：
   - 第一帧用实测位置播种（两路都回过位置才允许播种）；
   - 目标按**实际发给驱动器的转速**推进：`pos += rpm × 6°/s × dt`；
   - 跟随误差限幅 ±90°；
   - 停车 = 目标不再推进（位置环自己锁住），**不切模式、不发刹车**。
3. **诊断帧 36 → 40 字节**：新增 `[34-35]` `[36-37]` = 左右驱动器实测位置（度）；
   `flags` 新增 **bit6** = 两路位置回码都收到过。

### 工具（`tools/decode_diag.py`）

- `DIAG_SIZE` 36 → 40，解析并显示 `pos=左/右°`，`flags` 支持 bit6。
- **新增 `--diag-size N`**：帧长对不上时症状是"收不到任何诊断帧"，和"串口坏了/
  固件没发"长得**一模一样**，极难查。烧 main 分支的固件时用 `--diag-size 36`。

## 一个还没验证的前提（★ 重要）

**位置指令的语义假设是"绝对值"** —— 即 `data[2..3]` 和回码 `DATA6/7` 在**同一个
参考系**（驱动器自己的多圈计数）。这类 FOC 驱动器通常都是这样，但**没有实测确认过**。

如果它其实是**相对值**（即"再转多少度"），那么这一版会命令 `m_pos + 增量` —— 那是
一个很大的相对量，**轮子会猛地转一大圈**。

**所以第一次上电必须轮子悬空**，并且第一件事是看 `pos=` 那两个数：

| 看到什么 | 说明 |
|---|---|
| `pos=` 一直是 0 / 不动 | 位置回码没通（`DLC<8`）→ `flags` 里不会有 `驱动器位置回码OK` |
| `pos=` 随轮子转动而变、数值连续 | 回码通了，记下**分辨率**（转一圈变多少度） |
| 发一点点速度，`pos=` 变化量 ≈ 期望 | ✓ 语义对上了 |
| `pos=` 变化量远大于期望 | ✗ 语义是相对值 → 立刻断电，回来改 `pos_t = 增量` |

## 怎么测

```bash
# 0) 轮子**悬空**（垫起来），人守在电闸旁边
touch /tmp/chassis_watchdog.pause
# Ctrl-C 停掉 ROS 底盘栈

# 1) 先只看位置回码, 一格速度都不发
python3 ~/chassis_tools/decode_diag.py -p /dev/wheeltec_controller
#    看: flags 有没有 "驱动器位置回码OK"、pos= 那两个数转轮子时变不变

# 2) 发一点速度, 看位置跟不跟得上
python3 ~/chassis_tools/decode_diag.py -p /dev/wheeltec_controller --drive 0.10 0
#    0.10 m/s 很慢, 悬空时是安全的。看 pos= 的增量是否符合期望:
#    0.10 m/s -> 单轮 9.3 RPM -> 56 度/秒 -> 每秒涨约 56 度

rm /tmp/chassis_watchdog.pause
bash ~/chassis_tools/chassis_bringup.sh start
```

**位置模式下的"停"**：命令速度归零后目标不再推进，**驱动器位置环会把轮子锁在
当前位置** —— 推它会有反抗力。这是设计行为，也正好是当初想要的"没命令时锁死"。

**急停**：Ctrl-C 掉发布者 → STM32 的运动看门狗 800 ms 后把目标冻结（保持位置），
或者直接断电。

## 怎么退回

```bash
# 方式一: 把宏改回 0 重烧 (保留新加的位置回读, 只是不用它驱动)
#         main.c:  #define DRIVE_MODE_POSITION   0
# 方式二: 整支分支丢掉, 回到 main
git checkout main
```

`DRIVE_MODE_POSITION 0` 时编译出来的就是**原来的速度模式**，位置回读和 40 字节
诊断帧仍然保留（方便对照）—— 所以这一版不会污染 main 的行为。

## 要拿什么数据来判断"准不准"

用**同一套**已经验证过的工具，才能和 main 上的基线直接对比：

```bash
# 直线: 均值/5~95%区间/真实偏航
python3 ~/chassis_tools/straight_quality.py 0.30 10

# 单独看 IMU 噪声和零偏(顺带确认 IMU 是活的)
# 同上一条命令里已经有

# 原地转
bash ~/chassis_tools/turn_sweep.sh
```

**main 分支的基线（可直接对照）**：

| 指标 | main（速度模式） |
|---|---|
| 直线均值 | 0.276 m/s = **92%**（另一趟 99%） |
| 5~95% 区间宽度 | 待测（峰峰值 139% 被单帧残值污染） |
| 一次过冲 | 到 **138%**，约 3 秒落回 |
| 真实偏航 | −0.36° / 3 m = **0.12°/m** |
| 里程计偏航 vs IMU | **−0.08°**（0.03°/m） |
| 原地转 4 秒总角度 | **95~102%** |

**位置模式要赢，得赢在这几个上**：过冲（138% → ?）、低速精度（0.15~0.22 m/s
那一档 main 只有 64~77%）、以及定位的重复性。**如果它没能在这些上明显更好，
那这个方向就不值得继续** —— 位置模式还多了一个"位置计数器语义/回绕"的长期风险。
