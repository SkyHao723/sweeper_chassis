# 缓起缓停（斜坡）实车实测 + 驱动器速度环抖动定位

**日期**：2026-11-06
**被测车**：洗地车（scrubber，`TRACK_WIDTH_MM=456`，轮半径 0.0855 m）
**固件**：`ecd18f2`（v3，含缓起缓停 `RAMP_VX_ACC=1.0 / DEC=1.5` + 心跳看门狗），
刷的是 **scrubber hex 34333 B MD5 `8C12679E8ED7DFD66DCD7DA9E4C6ED0B`**，
烧录用 DAPLink（Horco CMSIS-DAP v2）+ openocd，独立回读 MD5 一致。
**主机**：`192.168.5.7`（RK3588），串口 `/dev/wheeltec_controller -> ttyUSB10`，
**不开 ROS**，由 `tools/ramp_test.py` 直连 115200 发帧、20 Hz 收帧。
**车状态**：**在地面上**（未架空），可以小幅动作。

## 1. 结论摘要

| 问题 | 结论 |
|---|---|
| 固件斜坡生效了吗 | **生效，且数值准确**。目标 ω 严格按 1.0 m/s² 爬升，200 ms 到顶，误差 0.4% |
| 回零准吗 | 准。按 1.5 m/s² 回零，实测 141~184 ms（含 0~20 ms 控制拍 + 50 ms 上报量化） |
| "起停猛"治好了吗 | **治了一半**。起步/停车的斜率不再突变，但驱动器速度环**欠阻尼**：阶跃超调 **+37%**，随后以 **~4 Hz、±8~10%** 持续振铃 ≥1 s |
| 车真的在抖吗 | **是**。两轮速度振荡相关系数 **+0.91~+0.98**（同相），且用户目视确认"一顿一顿 / 明显前后窜" |
| 该谁治 | **驱动器速度环**（`KP_ASR/KI_ASR/Deta/I_BW`），不是固件斜坡。斜坡只能降低加速度激励，消不掉环本身的阻尼不足 |

## 2. 怎么测的

`tools/ramp_test.py`（直连串口，不经 ROS，不受厂商节点 20 Hz 量化影响）：

- 50 Hz 发 11 B 速度帧（`vx_mm` int16 BE，`wz=0`），
- 同时收 44 B 诊断帧（`0x7E…0x7D`，BCC=XOR[0..41]）→ 目标 ω `[10..13]`、实际 ω `[6..9]`，
  以及 24 B 遥测帧（`0x7B…0x7D`）；
- 阶段序列：`pre 0@0.6 s` → `+200 mm/s@1.6 s` → `0@1.6 s` → `−200 mm/s@1.6 s` → `0@1.6 s`
  循环 3 次 → `post 0@0.6 s`（每次阶跃走约 32 cm）；
- 全程 448 个诊断帧 / 964 个发送帧；`[30]=3`（v3 固件）、`[41]` bit7=0（没发心跳 → 老 800 ms 看门狗）、
  `flags=15`（两轮在线且使能，**运动过程中没有命令超时**）。

分析脚本：`tools/analyze_ramp.py`（阶梯增量、到顶时间、回零时间）。

## 3. 目标 ω（斜坡本体）

左/右目标 ω 序列（`scrubber` 两轮 `DM_DIR=−1`，故为负值；单位 0.01 rad/s）：

```
0     0    -46   -93   -163  -210  -233  -233  -233 ...
```

- 诊断帧 20 Hz，控制拍 20 ms → 每帧跨 2~3 拍，所以步长是 47 / 70（= 2~3 × 23.4）
- 峰值 **233.0**，理论值 `0.2 / 0.0855 × 100 = 233.9` → **误差 0.4%**
- 到 95% 用时 **238~247 ms** = 200 ms 斜坡 + 0~20 ms 控制拍 + 50 ms 上报量化 ✔
- 回零：起始 163~198 → 0 用 **141~184 ms**（理论 93 ms + 量化）✔

**斜坡这一段没有问题，可以定稿。**

## 4. 实际 ω（问题所在）

### 4.1 阶跃超调

| 阶段 | 到 90% | 峰值 | 峰值时刻（相对相位起点） |
|---|---|---|---|
| up0 / down0 | 302 / 301 ms | 319 (137%) | +455 / +400 ms |
| up1 / down1 | 297 / 295 ms | 315 (135%) | +398 / +393 ms |
| up2 / down2 | 289 / 288 ms | 319 (137%) | +444 / +388 ms |

目标在 200 ms 就到顶了，实际在 ~400 ms 才冲到 **137%**，多走的 200 ms 就是速度环振铃。

### 4.2 巡航段持续振铃

巡航段（相位后半段，目标恒定 233）：

| 阶段 | L 均值 | L std | R 均值 | R std | 两轮相关系数 | 折算纹波 |
|---|---|---|---|---|---|---|
| up0 | 231.6 | 18.6 | 232.4 | 19.5 | +0.91 | ±8% / ±0.016 m/s |
| down0 | 226.4 | 21.8 | 226.6 | 22.3 | +0.98 | ±10% / ±0.019 m/s |
| up1 | 232.9 | 18.7 | 232.9 | 20.3 | +0.98 | ±8% |
| down1 | 227.6 | 21.2 | 226.1 | 21.1 | +0.98 | ±9% |
| up2 | 230.8 | 18.7 | 232.9 | 19.8 | +0.98 | ±8% |
| down2 | 226.2 | 22.1 | 226.8 | 22.3 | +0.98 | ±10% |

- **均值对**（226~233，目标 233，偏低 0~3%）
- **std 19~22 个计数 = ±8~10%**，相邻峰值间隔 0.20~0.26 s → **主频 ≈ 4 Hz**
- 两轮**同相**（相关 +0.91~+0.98）→ 不是差速/逆解的问题，是**车体整体前后窜**
- 折算车体位移幅度约 **±2 mm @ 4 Hz**（±0.018 m/s ÷ 2π×4 Hz）
- **用户目视确认**："一顿一顿 / 明显前后窜"

### 4.3 回零

实际 ω 衰减到起始值的 20% 用 **236~248 ms**、到 10% 用 242~545 ms
（目标侧 140 ms 就归零了，剩下的 ~100~400 ms 是机械惯性 + 驱动器减速）。

## 5. 根因判断

测出来的特征（4 Hz、ζ≈0.15、超调 37%、阶跃后振铃 ≥1 s）是典型的**欠阻尼二阶速度环**：

```
ω_n ≈ 2π×4 ≈ 25 rad/s，ζ ≈ 0.15
```

- 我们的固件只写 `CTRL_MODE(0x0A)=3`，**从没配过** `KP_ASR(0x19) / KI_ASR(0x1A) / I_BW(0x18) /
  Deta(0x1F) / ACC(0x04) / DEC(0x05)`，全部是出厂默认值；
- 手册里 `Deta` 是"速度环阻尼，1~30"，出厂默认未知——**大概率偏低**；
- 斜坡降低的是"目标变化率"，但速度环自身的闭环阻尼与目标斜率无关，
  所以斜坡能把"硬起硬停"变成"抖着起抖着停"，治不了 4 Hz 振铃。

另一个可能的（次要）因素是**低速轮地粘滑**：0.2 m/s 时轮子只有 0.37 转/秒，
橡胶轮在地面上的静/动摩擦切换也会产生 1~5 Hz 的极限环。**判据很简单：架空再跑一遍同样阶跃**——
振荡消失 = 粘滑/负载；振荡还在 = 纯速度环。

## 6. 后续可选方案（按代价排序）

| 方案 | 做法 | 代价 | 预期效果 |
|---|---|---|---|
| **A. 读回驱动器参数** | 固件加 `0x33` 参数读（`0x7FF` + `[idL,idH,0x33,RID,0,0,0,0]`，收帧后存表），再加进诊断/新帧报给上位机 | 固件 +60~80 行，重烧一次 | 知道 `KP_ASR/KI_ASR/Deta/I_BW/ACC/DEC/TIMEOUT` 的真实出厂值，才能有的放矢 |
| **B. 调阻尼/增益** | 写 `Deta` 调大、`KP_ASR` 调小、`ACC/DEC` 与固件斜坡对齐 | 依赖 A；每改一次要写参数并复测 | 直接压掉 4 Hz 振铃与 37% 超调 |
| **C. 固件加外环阻尼** | 用实际 ω 的微分反向微调目标 ω | 固件 +40 行，**但违反"底盘只做忠实执行器"的分工原则**，且与驱动器内环串级易互激 | 不推荐 |
| **D. 架空复测** | 不烧固件，10 秒判定 | 人工抬车 | 判别"粘滑" vs "速度环" |
| **E. 接受现状** | 斜坡已使起停斜率可控 | 0 | "一顿一顿"仍在，只是不硬起硬停了 |

> 当前状态：用户指示 **"先不动，斜坡够用了"**（m03762 之前的选择），
> 本文档只记录实测与定位，未改固件。要治 4 Hz 抖动，从 A 或 D 开始。

## 7. 附带发现：这台车的 IMU 是死的

`tools/imu_probe.py`（静态 3 s，只发 0 速度）读出来的：

```
[31] IMU status = 1        ← 状态非 OK
[38] IMU addr   = 0        ← 从来没扫到地址（YbImu 应为 0x23）
[39] IMU probe  = 0
[40] IMU version= 0
24 B 遥测帧：ax/ay/az/gx/gy/gz 全部恒为 0（vx=+2 mm/s 正常，来自轮速）
```

即 **24 B 遥测帧里的六轴是假数据（全零）**，上位机 `/imu/data_raw` 拿到的也是零，
`wheeltec_ekf` 若拿它做融合会得到无意义的结果。要么 IMU 没焊/没接（YbImu 在 PB10/PB11），
要么 I2C 没通。诊断帧 `[31]/[38]/[39]/[40]` 就是为查这个留的字段。

## 8. 复现

```bash
# 主机 192.168.5.7（smart / 12345678）
# 1) 确保没有 ROS 节点占串口
pgrep -af wheeltec_robot_node     # 应为空
# 2) 上传并跑（约 21 s，车会 ±0.2 m/s 来回 3 次，每次 ~32 cm）
python3 /tmp/ramp_test.py --speed-mm 200 --cycles 3 --out /tmp/ramp_test3.json
# 3) 拷回本地分析
python tools/rsh.py 192.168.5.7 12345678 --get /tmp/ramp_test3.json ramp_test3.json
python tools/analyze_ramp.py ramp_test3.json
```

本机上传：

```powershell
python tools\rsh.py 192.168.5.7 12345678 --put tools\ramp_test.py /tmp/ramp_test.py
```
