# 分工：谁该干什么（STM32 ↔ RK3588）

> **这份文档只回答一个问题：每件事该谁做。**
>
> 姊妹文档是 [`ros-integration.md`](ros-integration.md)（怎么接、怎么启、实测过什么）。
> 那份是**接入指南**，这份是**责任边界**。两边内容不重复：那边写"怎么做"，
> 这份写"谁做"。
>
> **为什么要写下来**：2026-10-13，底盘固件里被加进一个"用 IMU 保持航向"的控制器，
> 事后才发现主机侧**早就有一个**（`~/wheeltec/src/straight_line_drive`）。两个控制器
> 抢同一个自由度，两个积分环串联必然互绕。**问题不是那次改错了，而是分工从来没写下来。**

---

## 0. 一句话版

> **STM32 管「不失控、如实上报」；RK3588 管「要去哪、怎么去」。**
> **底盘不做决定，只做动作；主机不做实时，只做判断。**

## 2. ★ 时间尺度分界线（整份文档最重要的一张表）

**唯一的判据是：这件事需要多快。**

| 层 | 时间尺度 | 归属 | 内容 |
|---|---|---|---|
| **实时/安全层** | **< 1ms ~ 100ms** | **STM32** | 协议转换、看门狗、故障停车、执行器补偿、失控保护 |
| **估计/控制层** | 10ms ~ 100ms | RK3588 | 里程计、IMU 转发、EKF、速度/航向闭环 |
| **决策层** | 100ms ~ 秒 | RK3588 | 定位、建图、规划、避障、任务调度 |

**为什么分界线在 ~100ms：**
RK3588 是**非实时** Linux。它能"平均 50Hz"，但**没有任何实时保证** —— 一次调度抖动、
一次磁盘 IO，就可能几十毫秒不见人。**凡是"晚 100ms 就会出事"的动作必须放在 STM32。**

**★ 直接推论：**
**航向保持（几十~几百 ms 级）正落在分界线附近。主机已经做了，底盘就不要再做第二遍。**
这不是"谁做得更好"的问题 —— 两个环串联必然互绕。

## 3. STM32 的职责

### 3.1 必须做（做了才有这个底盘）

| 职责 | 为什么必须在底盘 |
|---|---|
| **USART ↔ CAN 协议转换** | 主机没有 CAN；且必须 20Hz 持续发（停发 800ms 驱动器即停） |
| **(vx,wz) → 左右轮 RPM 逆解** | 差速运动学 `v_l = vx − wz·b/2` |
| **轮速 → (vx,wz) 正解** | **只进诊断帧**给测试用；**不发布给主机**（见 §3.2） |
| **运动看门狗 800ms** | 主机挂了/线掉了，车必须自己停 |
| **链路看门狗 800ms** | 断链要断继电器（滚刷/水泵不能一直转） |
| **IWDG 独立看门狗** | 固件跑飞要能自复位 |
| **驱动器故障码 → 停车** | 过流/欠压/堵转必须立刻停，不能等主机 |
| **驱动器就绪联锁** | 两个驱动器没都回码时只发刹车 —— 防"单轮出力 = 原地打转" |
| **接收缓冲溢出 → 停车** | 协议帧乱掉时宁可停 |
| **继电器保持** | 显式开的继电器要一直保持；断链自动断 |

### 3.2 做，但**只作为执行器补偿**（不构成"第二个控制器"）

| 职责 | 边界 |
|---|---|
| **轮速外环 Trim**（补驱动器速度环稳态误差）| 只修**稳态偏差**；输出永远落在名义值的 `[0.8, 1.2]` 倍内、方向不变 |
| **起步助推 Boost**（破静摩擦）| 只在起步那一段；实测关掉后 4 次有 2 次起不来，所以留着 |
| **偏航失控制动**（2026-10-13 新增）| **只做失控保护，不做航向保持**：偏差 < 0.25 rad/s 时**一点都不动**，超过且持续 150ms 才给反向大差速 |

**★ 这三条的共同特征：它们都是"让底盘更忠实地执行 (vx,wz)"，而不是"替主机做决定"。**

### 3.3 绝对不能做

| 不能做 | 为什么 |
|---|---|
| **发布 `/odom` / TF** | 主机要拿**原始轮速**自己算里程。底盘再算一遍 = 两套里程打架，且极难发现 |
| **位姿/航向/位置闭环** | 和 Nav2/EKF 抢同一个自由度（就是开头那次教训） |
| **路径规划 / 避障** | 底盘没有地图、没有雷达 |
| **改动要转发给主机的 IMU 数据** | EKF 要原始值；喂滤波后/残差会破坏它的一致性假设 |
| **屏蔽或吞掉驱动器故障** | 故障必须上报让决策层处理；底盘只负责"停下并上报" |
| **依赖主机维持安全** | 安全是底盘自己的责任，主机会挂 |

## 4. RK3588 的职责

### 4.1 必须做

| 职责 | 备注 |
|---|---|
| **串口驱动**：24B 主遥测 → 轮速 → `/odom`；IMU 原始 → `/imu/data_raw` | 厂商包 `turn_on_wheeltec_robot` |
| **底盘几何参数**（轮径/轮距）→ 决定 `/odom` 尺度 | ⚠️ 有已埋的雷，见 §6.4 |
| **EKF 融合** `/odom` + `/imu` → 位姿 | 配置需与几何一致 |
| **定位/建图** | cartographer / FAST-LIO / AMCL |
| **Nav2** | 规划、代价地图、恢复行为 |
| **航向保持（走直）** | `~/wheeltec/src/straight_line_drive`，锁航向 + 自适应前馈补偏置 |
| **任务层** | `sweeper_stack` / `open_mower_ros` |

### 4.2 绝对不能做

| 不能做 | 为什么 |
|---|---|
| **依赖 100ms 以内的实时性** | 非实时 OS，做不到 |
| **假设底盘会自己保持航向/位置** | 契约里没有这一条（见 §5） |
| **和别的程序同时占串口** | 两个进程读同一个 tty，字节被随机分走 → **双方都拿到残帧且不报错**。实测踩过，白测一整轮 |
| **把底盘几何写错** | 里程尺度错 → 导航朝错误方向修 → **跑偏/蛇形，而且会被误诊成底盘问题** |
| **在底盘侧加闭环时不同步底盘负责人** | 见 §8 变更流程 |

## 5. 接口契约

### 5.1 STM32 → RK3588

| 内容 | 帧 | 频率 | 谁用 |
|---|---|---|---|
| 电池电压、陀螺仪三轴、加速度三轴、**左右轮转速** | 24B 厂商主遥测帧 | 定时上报 | 厂商节点 → `/odom` + `/imu/data_raw` |
| 模式/故障/电流/目标转速/CAN 计数/看门狗状态/**车型号**/自检结果 | **0x7E 诊断帧 36B** | 20Hz | **只有我们的工具**（厂商节点整帧跳过，**所以改长度是安全的**）|

### 5.2 RK3588 → STM32

| 内容 | 频率 | 断链行为 |
|---|---|---|
| `(vx, wz)` | 20Hz 持续 | 800ms 无帧 → 底盘自己刹车 |
| 继电器 | 20Hz 持续 | 800ms 无帧 → 底盘自己断开 |

### 5.3 契约原文（一句话）

> **底盘是「忠实的速度执行器」：给 `(vx, wz)`，它就真的走出 `(vx, wz)`。**
> **不保证航向、不保证轨迹、不保证停在原地。**

## 6. 三条设计原则

### 原则 1：底盘是「忠实的速度执行器」
给 `(vx,wz)` → 真的走出 `(vx,wz)`。**推论**：底盘里不能有依赖路径的闭环。
**理由**：主机已经有位姿环（EKF/Nav2），底盘再加一个就是抢同一个自由度。

### 原则 2：快的事归 STM32，慢的事归 3588
分界 ≈ 100ms（§2）。落在分界附近、主机已经做过的事（航向保持）→ **底盘不重复做**。

### 原则 3：宁可"少做"，不要"抢着做"
底盘多做的每件事都可能和主机打架，**而且很难发现**（两个环都"在正常工作"，只是互相拆台）。
**加任何底盘级闭环之前，先问：主机是不是已经在做这件事了？**

## 8. 缺口与归属建议

### 8.1 堵转实时识别 → **应该移到 STM32 固件**
- 判据（已在测试工具里用真实日志验证过）：
  `|目标| ≥ 20 RPM 且 |实际| < 5 RPM 且 |电流| ≥ 2.0A`，持续 ≥ 400ms
- **为什么归底盘**：这属于"晚 100ms 就出事"（继续灌电流 = 纯发热，实测见过 0 RPM 吃 43A）；
  而且**主机看不到单轮堵转**（它只拿到轮速）
- **判出来怎么办**：**停车 + 在诊断帧里报出来**，**不要自作主张"试图脱困"**
- 附带价值：它同时能**把无效的测试数据标出来**（见 §8.7）

### 8.2 走直精度 → **归主机**（工具已有）
- `~/wheeltec/src/straight_line_drive`，ROS2 action `/drive_straight`
- **它自带指标**：`final_yaw_error`、`lateral_estimate` —— 这就是"直不直"的定义值
- **底盘只需要不是猪队友**：不抢、不失控
- ⚠️ 已知结论（`README.md`"直线精度的锅不在外环"）：**直线的锅在驱动器内部速度环**，
  外环够不着（实测过冲约 186%）。所以这件事的解法在**主机侧闭环**和**驱动器**，
  不在底盘再加一个环

### 8.3 转弯精度 → **归主机**（有工具，已部分解决）
- 工具：`tools/turn_truth.py`（同时记 `/odom`、`/odom_combined`、`/imu/data_raw`，梯形积分）
- 已查明（`ros-integration.md` §4.6）：**里程计是诚实的，是车真没转够**（原地转 81%/71%）
- **底盘侧的外环修正已上车验证有效**（原地转 95~102%）
- **还缺**：命令转角 vs 实际转角的**闭环**（目前只有外环修轮速，不是修角度）

### 8.4 里程几何 → **归主机，而且是个已埋的雷**
- `ros-integration.md` §4.5 已记：**别用"命令值 vs /odom"验证轮径**（同一个常数，比值恒为 1），
  轮径要**单独量**（胎上贴标记推 2 米数圈数）
- ⚠️ **2026-10-13 新发现（洗地机侧）**：OpenMower 的 `hardware_specific/*/params_v2.yaml` 里
  是**别的割草机**的值（`Sabo: wheel_distance_m 0.45 / ticks_per_m 1195`，
  `YardForce: 0.325 / 1600~1964`），而洗地机轮距是 **0.425**；
  且 `hardware_specific/CUSTOM/` 里**只有 `default_environment.sh`，没有 `params_v2.yaml`**。
  **后果**：里程尺度错 → 导航朝错误方向修 → 跑偏/蛇形，**会被误诊成底盘问题**
- **动作**：核对洗地机实际生效的几何配置；补一次轮径/轮距标定

### 8.5 零速保持（"速度0时人推不动"）→ **归底盘，但有硬约束**
- **只能靠力矩模式**（速度模式刹车帧没有静止保持力）。
  ⚠️ 但 **`CTRL_ENABLE + 0` 是否自带保持力尚未实测** —— 值得先花 5 分钟验证，
  如果成立就不需要力矩模式
- **★ 它和"忠实的速度执行器"有张力**：
  - Nav2 期望的"0"是**不受力就停下**，不是**锁在原地**
  - 位置保持会让 Nav2 的微小速度命令"先突破保持力才动" → 表现为巨大静摩擦
  - 危险面：Nav2 有时**故意让车被推/被拖**（卡住后释放），保持环会死扛到电流上限
- **必须有的约束**：
  1. 只在"目标 = 0 **持续一段时间**"后才激活
  2. 收到任何非零速度命令 → **立刻平滑释放**
  3. 保持电流有硬上限 + 持续时间退避（否则持续发热）
  4. **有开关能整体关掉**，并明确告知导航侧

### 8.6 串口独占仲裁 → **归主机**（约定 + 自检，已有雏形）
- 两个进程同时读同一个 tty → 字节被随机分走 → **双方都拿残帧且不报错**（实测白测一整轮）
- 已有：`ros-integration.md` §4.6 记的"三个工具会自检 `/cmd_vel` 发布者数"、
  `decode_diag --drive` 需要先 `touch /tmp/chassis_watchdog.pause`
- **还缺**：一条明文约定 —— 任何测试前先确认"谁在控制串口"，并**写进测试记录**

### 8.7 测试有效性判定 → **已加在工具里，建议同时进固件**
- `tools/decode_diag.py` 现在会实时识别「堵转 / 偏航失控」，**认出就立刻停车并把这次判为无效**
- 用法：`--classify-selftest`（不需要硬件，6 个用例全过）、`--classify <日志>`（复核历史数据）
- **为什么必须有**：实测出现过"轮子 0 RPM 却吃 43A"，它既可能是**驱动器故障**、
  也可能是**车头顶到墙**。分不清这两者，**任何"走直/转准"的结论都不成立** ——
  这条已经导致过一次错误结论被收回

### 8.8 雷达
- **未安装** → SLAM / Nav2 的唯一环境输入缺失（`ros-integration.md` §7）
- 装上后要改 `robot_model.yaml` 的 `base_to_laser`（**主机侧**）

## 10. 变更流程约定（避免再出现"两边都在修同一件事"）

| 要改的东西 | 必须做 |
|---|---|
| **底盘级闭环/补偿**（Trim / Boost / 失控制动 / 任何新环）| **先问"主机是不是已经在做这件事"** |
| 主机侧的底盘几何参数 | 改完**通知底盘侧**（会改变 `/odom` 尺度）|
| 诊断帧格式 | 同步改 `tools/decode_diag.py`（`0x7E` 自定义帧，**改长度安全**）|
| 上电自检 | 提醒：**自检会让车自己窜一下**，上车前记得关 |
| 任何运动测试 | 先确认**场地空、无人干预、串口独占**；跑完**必须看 `decode_diag.py` 的有效性判定** |
| 任何"硬件坏了"的结论 | 先排除**堵转（顶到东西）** —— 跑一次判定器，或把驱动轮垫起来空转 |
