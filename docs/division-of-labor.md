# 分工：谁该干什么（STM32 ↔ RK3588）

> **这份文档只回答一个问题：每件事该谁做。**
>
> 姊妹文档是 [`ros-integration.md`](ros-integration.md)（怎么接、怎么启、实测过什么）。
> 那份是**接入指南**，这份是**责任边界**。两边内容不重复：那边写"怎么做"，
> 这份写"谁做"。
>
> **为什么要写下来**：2026-10-13，底盘固件里被加进一个"用 IMU 保持航向"的控制器，
> 事后才发现主机侧**早就有一个**（`~/wheeltec/src/straight_line_drive`）。两个控制器
> 抢同一个自由度，两个积分环串联必然互绕。**问题不是那次改错了，而是分工从来没写下来。**

## 0. 一句话版

> **STM32 管「不失控、如实上报」；RK3588 管「要去哪、怎么去」。**
> **底盘不做决定，只做动作；主机不做实时，只做判断。**

## 2. ★ 时间尺度分界线（整份文档最重要的一张表）

**唯一的判据是：这件事需要多快。**

| 层 | 时间尺度 | 归属 | 内容 |
|---|---|---|---|
| **实时/安全层** | **< 1ms ~ 100ms** | **STM32** | 协议转换、看门狗、故障停车、执行器补偿、失控保护 |
| **估计/控制层** | 10ms ~ 100ms | RK3588 | 里程计、IMU 转发、EKF、速度/航向闭环 |
| **决策层** | 100ms ~ 秒 | RK3588 | 定位、建图、规划、避障、任务调度 |

**为什么分界线在 ~100ms：**
RK3588 是**非实时** Linux。它能"平均 50Hz"，但**没有任何实时保证** —— 一次调度抖动、
一次磁盘 IO，就可能几十毫秒不见人。**凡是"晚 100ms 就会出事"的动作必须放在 STM32。**

**★ 直接推论：**
**航向保持（几十~几百 ms 级）正落在分界线附近。主机已经做了，底盘就不要再做第二遍。**
这不是"谁做得更好"的问题 —— 两个环串联必然互绕。

> **★ 安全注（2026-10-13 失控事件后复查）**
>
> `Cmd_Apply` 里有一条**已经存在的、很关键的防护**：
> ```
> /* 协议里的其它功能帧: 本工程没实现, 必须忽略 ----
>  * ★ 绝对不能当速度帧解析 —— 那样 f[3..8] 会被误读成 vx/wz, 车会乱窜。 */
> ```
> 也就是"灯带 / 回充 / 安全防护"这些帧**不会被当成速度帧**。这条在，是对的。
>
> **但另一个坑仍然存在**：速度帧只夹到
> `MAX_LIN_SPEED`（= `MAX_RPM × 周长 / 60` = 洗地机 **1.571 m/s**）、
> `MAX_YAW_RATE`（3.0 rad/s）。**这是"设计上限"，不是"合理性闸门"** ——
> 一条 BCC 恰好合法的垃圾帧、或一份跑飞的代码，都能让指令**直接到顶**。
> 而且 `ACCEL_STEP_MS = 0`（**阶跃，没有加速斜坡**）→ 顶到上限就是"瞬间最大速度"。
>
> **待办：加"指令合理性"检查（跳变率限制 / 连续 N 帧一致才认）。见 §8.9。**

> **★★ 关键更正（2026-10-13，我上一版文档写错了）**
>
> 上一版里我写"轮速 → `(vx,wz)` 正解**只进诊断帧、不发给主机**" —— **这是错的。**
>
> 实际是：`Send_MainTelemetry` 把**固件自己算出来的** `body_vx` / `body_wz` 填进了
> 24 字节帧的 `[2-3]/[4-5]` 和 `[6-7]`。**而这个帧里根本没有"左右轮速"字段。**
> 厂商节点拿到它**直接当 `/odom` 的 twist 用**（`ros-integration.md` §4.6 记的
> "STM32 轮速 → 24B 遥测 [6-7]=wz → 厂商节点直接取用"就是这个意思）。
>
> **所以：里程计的"刻度"在底盘侧** —— 用的是固件里的 `WHEEL_CIRC_M` / `TRACK_WIDTH_M`。
>
> 三个直接推论：
> 1. **改固件里的轮径/轮距 = 改整条链路里唯一的里程刻度** —— 这是底盘侧的责任
> 2. 这也解释了为什么"命令值 vs `/odom`"验不出轮径：**两边用的是同一个常数**
> 3. **底盘侧算错 `(vx,wz)` 会直接污染 EKF 的输入**，而看 `/odom` 是看不出来的

### 3.12 STM32 **不干什么** —— 逐条

| 不做什么 | 取证 | 为什么 |
|---|---|---|
| **不发布里程计** | 没有 `Odom_Publish`；`Odom_Tick` 只是"刷新传感器"，不组装 ROS 消息 | 底盘只上报原始量，`/odom` 由主机组装 |
| **不发布 TF** | 无 | TF 树在主机侧（`robot_model.yaml`）|
| **不做位姿闭环** | 没有 `Pose_Hold` / `Go_To` | 和 Nav2/EKF 抢自由度 |
| **不做航向保持** | ★ `Yaw_Trim` **名字像但不是** —— 它是"偏差 > 0.25 rad/s 才介入"的**失控制动**，正常范围内一点都不动 | 主机侧 `straight_line_drive` 已经在做航向保持 |
| **不做位置保持 / 锁位** | 位置锁位**已经删掉**（曾导致实车失控）| 同上 |
| **不做路径规划 / 避障** | 无 | 底盘没有地图、没有雷达 |
| **不读写驱动器参数** | 无（协议**不暴露**参数读写，CAN/串口/BLE 三条路都确认过）| 硬件能力的硬边界，只能绕 |
| **不修改要转发给主机的 IMU 数据** | `IMU_AccelToRaw`/`GyroToRaw` **只做量纲换算**，不滤波、不出残差 | EKF 要原始值；喂滤波值会破坏它的一致性假设 |
| **不屏蔽驱动器故障** | `CAN1_Poll` 把故障码原样上报 | 故障给决策层处理，底盘只负责"停下 + 上报" |
| **不自作主张"脱困"** | 堵转/故障只停车上报，不尝试反向冲 | 未经判断的动作比停下来更危险 |
| **不依赖主机维持安全** | 看门狗 / IWDG 全在底盘 | 主机会挂 |

### 3.13 出问题的优先级（从高到低）

1. **`failsafe` / 看门狗** —— 断了就停，不看别的
2. **`Drive_Ready` 就绪联锁** —— 驱动器不全就只刹车
3. **`Yaw_Trim` 失控制动** —— 偏航失控时压住
4. **`Trim_Apply` / `Boost_Decide`** —— 只做微调
5. **主机命令** —— 最外层意图

**★ 底盘里任何新加的东西，都必须排在"主机命令"之后、且不能覆盖前四项。**

### 4.4 RK3588 **不干什么**

| 不做什么 | 为什么 |
|---|---|
| **不做 100ms 以内的实时动作** | 非实时 Linux，做不到；这类事在 §3 里 |
| **不假设底盘会自己保持航向/位置** | 契约里没有（见 §5）|
| **不和别的程序同时占串口** | 两个进程读同一个 tty → 字节被随机分走 → **双方都拿残帧且不报错**（实测白测一整轮）|
| **不改底盘侧的轮径/轮距** | ★ 里程刻度在**固件**里（见 §3.10 的更正），改主机侧的几何不影响 `/odom` |
| **不在底盘侧加闭环时不通知底盘负责人** | 见 §10 变更流程 |
## 5. 接口契约

### 5.1 STM32 → RK3588

| 内容 | 帧 | 频率 | 谁用 |
|---|---|---|---|
| 电池电压、陀螺仪三轴、加速度三轴、**左右轮转速** | 24B 厂商主遥测帧 | 定时上报 | 厂商节点 → `/odom` + `/imu/data_raw` |
| 模式/故障/电流/目标转速/CAN 计数/看门狗状态/**车型号**/自检结果 | **0x7E 诊断帧 36B** | 20Hz | **只有我们的工具**（厂商节点整帧跳过，**所以改长度是安全的**）|

### 5.2 RK3588 → STM32

| 内容 | 频率 | 断链行为 |
|---|---|---|
| `(vx, wz)` | 20Hz 持续 | 800ms 无帧 → 底盘自己刹车 |
| 继电器 | 20Hz 持续 | 800ms 无帧 → 底盘自己断开 |

### 5.3 契约原文（一句话）

> **底盘是「忠实的速度执行器」：给 `(vx, wz)`，它就真的走出 `(vx, wz)`。**
> **不保证航向、不保证轨迹、不保证停在原地。**

## 6. 三条设计原则

### 原则 1：底盘是「忠实的速度执行器」
给 `(vx,wz)` → 真的走出 `(vx,wz)`。**推论**：底盘里不能有依赖路径的闭环。
**理由**：主机已经有位姿环（EKF/Nav2），底盘再加一个就是抢同一个自由度。

### 原则 2：快的事归 STM32，慢的事归 3588
分界 ≈ 100ms（§2）。落在分界附近、主机已经做过的事（航向保持）→ **底盘不重复做**。

### 原则 3：宁可"少做"，不要"抢着做"
底盘多做的每件事都可能和主机打架，**而且很难发现**（两个环都"在正常工作"，只是互相拆台）。
**加任何底盘级闭环之前，先问：主机是不是已经在做这件事了？**

## 8. 缺口与归属建议

### 8.1 堵转实时识别 → **应该移到 STM32 固件**
- 判据（已在测试工具里用真实日志验证过）：
  `|目标| ≥ 20 RPM 且 |实际| < 5 RPM 且 |电流| ≥ 2.0A`，持续 ≥ 400ms
- **为什么归底盘**：这属于"晚 100ms 就出事"（继续灌电流 = 纯发热，实测见过 0 RPM 吃 43A）；
  而且**主机看不到单轮堵转**（它只拿到轮速）
- **判出来怎么办**：**停车 + 在诊断帧里报出来**，**不要自作主张"试图脱困"**
- 附带价值：它同时能**把无效的测试数据标出来**（见 §8.7）

### 8.2 走直精度 → **归主机**（工具已有）
- `~/wheeltec/src/straight_line_drive`，ROS2 action `/drive_straight`
- **它自带指标**：`final_yaw_error`、`lateral_estimate` —— 这就是"直不直"的定义值
- **底盘只需要不是猪队友**：不抢、不失控
- ⚠️ 已知结论（`README.md`"直线精度的锅不在外环"）：**直线的锅在驱动器内部速度环**，
  外环够不着（实测过冲约 186%）。所以这件事的解法在**主机侧闭环**和**驱动器**，
  不在底盘再加一个环

### 8.3 转弯精度 → **归主机**（有工具，已部分解决）
- 工具：`tools/turn_truth.py`（同时记 `/odom`、`/odom_combined`、`/imu/data_raw`，梯形积分）
- 已查明（`ros-integration.md` §4.6）：**里程计是诚实的，是车真没转够**（原地转 81%/71%）
- **底盘侧的外环修正已上车验证有效**（原地转 95~102%）
- **还缺**：命令转角 vs 实际转角的**闭环**（目前只有外环修轮速，不是修角度）

### 8.4 里程几何 → **★ 在底盘侧（固件常数），不在主机侧**

> **更正**：我上一版写"里程几何归主机、且是个已埋的雷"。读了代码之后要改：
> **`(vx,wz)` 是 STM32 算好的**（`Wheel_Update` → `Send_MainTelemetry`），主机只是把它
> 组装成 `/odom` 消息。**所以"轮径/轮距"这个刻度在固件里**（`WHEEL_CIRC_M` /
> `TRACK_WIDTH_M`），见 §3.10。

- `ros-integration.md` §4.5 已记：**别用"命令值 vs /odom"验证轮径**（同一个常数，
  比值恒为 1），轮径要**单独量**（胎上贴标记推 2 米数圈数）
- **动作**：换胎/换轮子之后，**改固件常数**，而不是改主机参数
- ⚠️ 另一条独立的雷（**只在使用 OpenMower 那套时才相关**）：它自己的
  `hardware_specific/*/params_v2.yaml` 里是**别的割草机**的值
  （`Sabo: wheel_distance_m 0.45 / ticks_per_m 1195`，`YardForce: 0.325 / 1600~1964`），
  而洗地机轮距是 **0.425**；且 `CUSTOM/` 里**只有 `default_environment.sh`，
  没有 `params_v2.yaml`**。**如果那套栈真的在用，几何尺度错 → 导航朝错误方向修 → 跑偏**
- **动作**：确认洗地机实际生效的是哪套栈，再决定改哪边

### 8.5 零速保持（"速度0时人推不动"）→ **归底盘，但有硬约束**
- **只能靠力矩模式**（速度模式刹车帧没有静止保持力）。
  ⚠️ 但 **`CTRL_ENABLE + 0` 是否自带保持力尚未实测** —— 值得先花 5 分钟验证，
  如果成立就不需要力矩模式
- **★ 它和"忠实的速度执行器"有张力**：
  - Nav2 期望的"0"是**不受力就停下**，不是**锁在原地**
  - 位置保持会让 Nav2 的微小速度命令"先突破保持力才动" → 表现为巨大静摩擦
  - 危险面：Nav2 有时**故意让车被推/被拖**（卡住后释放），保持环会死扛到电流上限
- **必须有的约束**：
  1. 只在"目标 = 0 **持续一段时间**"后才激活
  2. 收到任何非零速度命令 → **立刻平滑释放**
  3. 保持电流有硬上限 + 持续时间退避（否则持续发热）
  4. **有开关能整体关掉**，并明确告知导航侧

### 8.6 串口独占仲裁 → **归主机**（约定 + 自检，已有雏形）
- 两个进程同时读同一个 tty → 字节被随机分走 → **双方都拿残帧且不报错**（实测白测一整轮）
- 已有：`ros-integration.md` §4.6 记的"三个工具会自检 `/cmd_vel` 发布者数"、
  `decode_diag --drive` 需要先 `touch /tmp/chassis_watchdog.pause`
- **还缺**：一条明文约定 —— 任何测试前先确认"谁在控制串口"，并**写进测试记录**

### 8.7 测试有效性判定 → **已加在工具里，建议同时进固件**
- `tools/decode_diag.py` 现在会实时识别「堵转 / 偏航失控」，**认出就立刻停车并把这次判为无效**
- 用法：`--classify-selftest`（不需要硬件，6 个用例全过）、`--classify <日志>`（复核历史数据）
- **为什么必须有**：实测出现过"轮子 0 RPM 却吃 43A"，它既可能是**驱动器故障**、
  也可能是**车头顶到墙**。分不清这两者，**任何"走直/转准"的结论都不成立** ——
  这条已经导致过一次错误结论被收回

### 8.8 雷达
- **未安装** → SLAM / Nav2 的唯一环境输入缺失（`ros-integration.md` §7）
- 装上后要改 `robot_model.yaml` 的 `base_to_laser`（**主机侧**）

### 8.9 指令合理性检查 → **★ 归底盘，2026-10-13 失控后新增的缺口**

- **现象**：2026-10-13 洗地机失控，实测抓到
  `1号 目标+200 实际 0 -40.2A | 2号 目标+190 实际+232 | wz=+4287mrad/s` ——
  **两份轮速指令都被顶到 `MAX_RPM=200`**（洗地机 1.57 m/s ≈ 5.7 km/h），
  一轮空转、一轮堵着灌 40A，于是"突然非常快"。
- **现在的防护**（已存在，但只到这里）：
  - `Cmd_Verify`：帧头 + 帧尾 + **BCC** 三重校验
  - `Cmd_Apply`：**非速度帧必须忽略**（这条注释写明"否则 f[3..8] 会被误读成 vx/wz，车会乱窜"）
  - 速度帧夹到 `MAX_LIN_SPEED` / `MAX_YAW_RATE`
- **缺的是**：
  1. **跳变率限制**：`ACCEL_STEP_MS = 0`（阶跃）。一条从 0 直接到上限的指令会被**无条件执行**。
     应该限制"单帧允许的速度变化量"（或直接启用加速斜坡）
  2. **合理性闸门**：连续 N 帧一致才认；或"指令超过 X 才要求更严格的校验"
  3. **失控后的自锁**：一旦检测到"指令顶到上限且无对应运动"，应当**锁存停车并上报**
     （和已有的 `failsafe_latched` 同一个思路）
- **为什么归底盘**：这是"晚 100ms 就出事"，而且主机此时可能正是故障源
- **★ 但必须说清**：如果根因是**固件本身跑飞/写坏**，任何应用层检查都救不了 ——
  所以这条只是"多一道闸门"，不能替代"烧录前断驱动电源"那条流程约束

### 8.10 ★ 把 44 字节诊断帧接到 ROS 侧（固件已做完，**缺主机侧补丁**）

**现状**：固件已经在向上发 44 字节诊断帧（左右轮速/目标/电流/故障码/饱和标志/
看门狗状态/底盘收到的指令），**但厂商节点按设计把整帧跳过**，所以数据到不了 ROS 侧。

**要做的**（位置已查到）：

| 文件 | 位置 | 改什么 |
|---|---|---|
| `~/wheeltec/src/turn_on_wheeltec_robot/include/.../wheeltec_robot.h` | `#define RECEIVE_DATA_SIZE 24` | 加 `DIAG_FRAME_SIZE 44`、帧头常量、新 publisher |
| 同上 | 类里的 publisher 列表 | 加 `/chassis_status`（先 `std_msgs/UInt8MultiArray` 跑通也行）|
| `src/wheeltec_robot.cpp` | 收帧解析（约 L750 "Read and verify the data … frame by frame"）| 在 24 字节帧之外**再识别 0x7E 帧**（头 0x7E / 尾 0x7D / BCC）→ 解析 → publish |

**为什么不会破坏现有功能**：厂商的入帧条件是"上一字节是帧尾 0x7D、本字节是 0x7B"，
而诊断帧头是 0x7E —— 所以**现在是整帧跳过**；显式识别只是**接管本来就被丢弃的字节**。

**验收（纯编译 + 话题验证，不需要动车）**：

## 10. 变更流程约定（避免再出现"两边都在修同一件事"）

| 要改的东西 | 必须做 |
|---|---|
| **底盘级闭环/补偿**（Trim / Boost / 失控制动 / 任何新环）| **先问"主机是不是已经在做这件事"** |
| **里程刻度（轮径/轮距）** | ★ 在**固件常数**里（见 §3.10）—— 换轮子改这里，不是改主机参数 |
| 诊断帧格式 | 同步改 `tools/decode_diag.py`（`0x7E` 自定义帧，**改长度安全**）|
| 上电自检 | 提醒：**自检会让车自己窜一下**，上车前记得关 |
| 任何运动测试 | 先确认**场地空、无人干预、串口独占**；跑完**必须看 `decode_diag.py` 的有效性判定** |
| 任何"硬件坏了"的结论 | 先排除**堵转（顶到东西）** —— 跑一次判定器，或把驱动轮垫起来空转 |
| **★★ 烧录 / 复位固件** | **必须先把驱动电源断开或把驱动轮架空**（2026-10-13 失控就是这么来的）；**烧完必须独立读回比对**，不能只信 `program` 的回显；**验证通过之前不允许整车带载上电** |
