# FOC 驱动器 CAN 协议（FOC_CH4-V1.2）—— 经厂家资料核实版

> **这是哪一层的协议**：**STM32 ↔ FOC 轮毂驱动器**（CAN 总线）。
> 不要和 [`chassis-serial-protocol.md`](chassis-serial-protocol.md) 混：
> 那一份是 **RK3588 ↔ STM32**（Wheeltec 那套 11 字节 `0x7B…0x7D` 帧）。
> 两层是**互补的两个链路**，帧格式完全不同。

**本文的性质**：我们原先是从协议 PDF 反推 + 示波器式试错得出这套协议的。
2026-10-11 拿到**电机厂家的参考资料包**后，逐条核对了一遍。
本文记录**核对结果**，并明确区分：

- ✅ **已在两处独立印证**（厂家 PDF 原文 + 厂家参考源码/上位机）
- ⚠️ **只有一处出处**，或 PDF 自相矛盾
- ❓ **仍未确定 / 必须实机实测**

## 1. 链路参数

| 项 | 值 | 出处 |
|---|---|---|
| 总线 | CAN **扩展帧**（29 位 ID）+ 8 字节数据，**500 kbps**，**120 Ω** 终端匹配 | PDF 第 3 章 |
| 为什么没有帧头帧尾 | PDF 原文：*"CAN 口通信自带底层校验故没有使用帧头帧尾区分数据帧完整性"* | PDF |
| 电机 ID 通式 | **`0x1N01E600`（N = 1…4）** | PDF 第 2 页给 4 个具体值；通式是⚠️推断 |
| 控制帧 ID | `0x1101E600`（1 号）/ `0x1201E600`（2 号）/ `0x1301E600`（3 号）/ `0x1401E600`（4 号） | PDF 第 2 页 + `esp_my.h:22-25` |
| **回码帧** ID | 控制帧 ID **+1** → `…E601` | PDF 2.2.1 + `can.c:134-137` |
| **定时上报帧** ID | 控制帧 ID **+3** → `…E603` | PDF 2.2.2 + `can.c:139-142` |

**拓扑**（PDF 第 2 页）：1 路串口只能控制**单台控制器的左右两路**电机；两驱默认分配 1/2 号；

> PDF 第 2 页有 2 张**内嵌实物照片**（`单个控制器-2驱动`、`2个控制器-4驱动`，贴纸标了 1/2 号）。

## 2. 控制帧（我们 → 驱动器）8 字节

**权威出处**：厂家 `send_cmd()`（`.doc/…/pwm_adc.c:273-286`），与 PDF 2.2.1 完全一致。

```c
// 厂家参考实现 send_cmd()
pwm_cmd[0] = m->control_mode;                    // 运行模式
pwm_cmd[1] = m->enable;                          // 控制字
pwm_cmd[2] = (m->cmd_value >> 8) & 0xFF;         // 设定值 高字节
pwm_cmd[3] =  m->cmd_value       & 0xFF;         // 设定值 低字节
pwm_cmd[4] = m->add_gain;                        // 加速间隔 Δt
pwm_cmd[5] = m->sdd_gain;                        // 减速间隔 Δt
pwm_cmd[6] = m->low_power;                       // 输入电源低压保护值
pwm_cmd[7] = 0;                                  // 预留
```

| 字节 | 含义 | 取值 |
|---|---|---|
| `data[0]` | 运行模式 | 见 §2.1 |
| `data[1]` | 控制字 | 见 §2.2 |
| `data[2..3]` | 设定值 `int16` **大端**（PDF 第 12 页：默认高字节在前）| 单位随模式变，见 §2.1 |
| `data[4]` | 加速间隔 Δt | `Uint8(0~100)` ms，**0 = 最快（直跳目标）**，默认 0 |
| `data[5]` | 减速间隔 Δt | 同上，默认 0 |
| `data[6]` | 输入电源低压保护值 | PDF `Uint8(0~100)` V；厂家上位机限 **10~60 V、默认 24 V** |
| `data[7]` | 预留 | 0 |

### 2.1 四种模式（✅ 两处印证）

| `data[0]` | 模式 | 设定值单位 | 量程 | 缩放 |
|---|---|---|---|---|
| `0x01` | **电压模式** | V | `0 ~ 10.0 V` | **×10**（写 0~100） |
| `0x04` | **★ 力矩模式** | A | `-10.0 ~ +10.0 A` | **×10**（写 -100~100，正负=扭矩方向） |
| `0x05` | **速度模式** | RPM | `-500 ~ +500` | **原值** |
| `0x06` | **位置模式** | ° | `-3600 ~ +3600`，360°/圈，**0° = 开机位置** | **原值** |

出处：PDF 第 4/8 页 + 上位机 `_modeDesc[8] = {"", "电压模式","2","3","力矩模式","速度模式","位置模式",""}`
（`.doc/…/MainWindow.xaml.cs:64-67`）+ 按钮映射（`:76-82` 电压→1、力矩→4、速度→5、位置→6）。

**★★ 我们曾经误判"扭矩模式 0x04 不存在" —— 这是错的。** 见 §7。

**模式 2 / 3 ❓ 未定义**：厂家自己的描述表里只写了字面字符串 `"2"`、`"3"`，
**全部厂家代码里从未被赋值过**。不猜。

### 2.2 控制字（✅）

| 值 | 含义 | 出处 |
|---|---|---|
| `0x01` | **使能**（模式生效） | PDF + 上位机 `:389` |
| `0x02` | **失能 / 空滑**（PWM 关闭，功耗变低）| PDF + 上位机 `:402`。**"松开/滑行"就是它**，没有单独的"松开"值 |
| `0x03` | **刹车**（急刹） | PDF + 上位机 `:415` |
| **`0x0F`** | **★ 复位（清故障）** | PDF + 上位机 `:428` |

> ⚠️ PDF 该表把类型写成 `Uint8(0～2)` 却又列了 `03`/`0F` —— **文档自身笔误**。

### 2.3 两条硬约束（只在 PDF 里，源码无体现）

1. **「模式切换需在电机停止空闲状态下生效」** —— 想切到位置模式/扭矩模式，**必须先停下来**。
2. **串口最小通信间隔 5 ms** —— 这是驱动器**串口**协议的限制；我们走 CAN，不受这条约束，
   但可以据此推断驱动器 MCU 不算快，我们 20 ms 一条 CAN 帧很宽裕。

### 2.4 加减速 Δt 的准确语义（⚠️ 只有 PDF 一处）

**不是"斜率"，而是"每 Δt ms 让目标值走 1 个 LSB"**，`Δt = 0` 表示直接跳到目标。

| 模式 | 1 个 LSB |
|---|---|
| 速度 | **1 RPM** ← 所以我们的 `ACCEL_STEP_MS`"ms per RPM"在这个模式下**近似成立** |
| 力矩 / 电压 | **0.1 A / 0.1 V** ← 其它模式要换算，不能照搬 RPM |

PDF 原文还定义了方向：*"定义正值为正方向，设置值大于当前值为加速，反之为减速；
当前 100 RPM 若设置 200 RPM 为加速，若设置 50 RPM 则为减速，设置为 -300 RPM 也是减速。"*

## 4. ★★ 定时上报帧 `…E603` —— **和 E601 结构完全不同！**

**这是最容易踩的坑。** 权威出处：PDF 第 6/10 页 + 上位机 `:173-180`。

| 字节 | 含义 | 单位/换算 |
|---|---|---|
| `DATA0` | **固件大版本号**（初始 1.1）| — |
| `DATA1` | **固件小版本号** | — |
| `DATA2` | 运行状态 / 故障码 | 见 §5 |
| `DATA3` | **电机 MOS 温度** | ℃（单字节），**默认超过 100 ℃ 报警停止运行** |
| `DATA4..5` | **电源输入电压** `int16` ×10 | **V×10**（→ mV 是 `×100`） |
| `DATA6..7` | 实际转速 `int16` | RPM |

- **默认 0.2 Hz（5 秒一次）**，PDF 原文"可按用户需求调整"。
- ❗ **绝不能拿 E601 的表去解析 E603** —— 那样会把**电压读成电流、版本号读成故障码**。
  必须按 ID 低字节（`01` / `03`）分支。
- ✅ **我们已经是分支处理的**：`main.c` 的 `MOTOR1_REPORT_ID` 分支只取 `DATA4..5` 当电压，
  **没有**误用 E601 的表。**那里不是 bug，别去"修"。**

### 4.1 由这一节推出来的一个旧谜团答案

我们代码里是：

```c
if (v10 > 0) battery_mv = (uint16_t)((int32_t)v10 * 100);
```

配上"E603 默认 **5 秒**才来一次" ⇒ **`battery_mv` 最多 5 秒才更新一次；
驱动器没上电时根本不会来 E603，于是电池一直是 0。**

这大概率就是之前 **`/PowerVoltage = 0.0`** 那个谜团的答案（当时驱动器没上电），
不需要再归因到"STM32 的 ADC 坏了"。

> ⚠️ 我们 README 里另有一句"电池只有 ~1.8 Hz（采样保持）"，**和 PDF 的 0.2 Hz 对不上**。
> 上报周期是可调的，所以可能被改过 —— 但**这条需要实机核实**：
> 如果真是 0.2 Hz，任何基于电池的保护逻辑都有 5 秒延迟。

## 6. ❗ 协议**不支持**的：驱动器参数读写

**结论：协议层完全没有 PID / 限流 / 极对数 / CAN 波特率 / CAN ID 的读写通路。**

- **CAN / 串口**：PDF 12 页没有参数读写章节；厂家上位机的"发送参数设置"按钮
  发的其实就是**同一条控制帧**（模式+状态+设定值+加速+减速+低压），不是寄存器写。
- **BLE**：厂家 ESP32 参考里有个 `0xF1…0x1F` 帧注释写着"**写参数**"，
  但读了源码（`.doc/…/ble_demo.c:568-581`）会发现它做的还是：

  ```c
  m1.control_mode = value[5];  m1.cmd_value = ...;   // 模式 + 设定值
  m1.add_gain = value[9];  m1.sdd_gain = value[10];  // 加速 / 减速 Δt
  m1.low_power = value[11];  m1.enable = value[12];  // 低压保护 / 控制字
  send_cmd(CAN_ID1, &m1);                            // ← 同一条 8 字节控制帧
  ```

  **"写参数"是个误名。** 另外 `0xF3` 帧设的 `max_rpm` 是 **ESP32 桥自己的
  输入缩放参数**（存在 SPIFFS 里），**不是驱动器参数**。
- 安卓 App `FOC-CH2.apk` 里有"读取/写入电机参数"按钮，但**字符串级分析取不到帧格式**，
  要反编译 Kotlin 才能确认 —— ❓ **未完成**。不过结合上面两条，很可能同样只是这套控制帧。

### 6.1 这条结论的直接后果（重要）

**协议上唯一能下发的配置只有两个**：`data[4]/[5]` 加减速 Δt、`data[6]` 低压保护阈值。

⇒ **驱动器速度环那个极限环（实测目标 27.9 RPM 时实际在 0↔71 RPM 之间暴冲），
我们没有办法通过调参解决。** 只剩两条路：

1. 找厂家调驱动器内部参数；
2. **STM32 切扭矩模式，自己做速度环** —— 而 §2.1 现在证明**扭矩模式确实存在**，这条路通了。

## 7. ★ 本次核对推翻/更正的东西

| # | 我们之前的假设 | 核对结果 |
|---|---|---|
| 1 | **"扭矩模式 0x04 不存在"** | ❌ **错**。PDF 第 4/8 页明写 `04: 力矩模式`，单位 A，×10。厂家上位机也印证。**而且证据一直在我们自己的 `docs/` 里** |
| 2 | 控制字只有 01/02/03 | ⚠️ 漏了 **`0x0F` 复位（清故障）** |
| 3 | E601 的字段表可以描述回码帧 | ⚠️ **E603 结构完全不同**，必须分支解析（我们代码已分支，但文档没写清）|
| 4 | 位置值只是"度" | ⚠️ 补：**±3600°，360°/圈，0° = 开机位置** |
| 5 | 速度量程按 200 | ⚠️ 驱动器文档量程是 **−500~+500 RPM**；我们的 200 来自厂家 ESP32 的 `max_rpm` 默认值（`main.c:63`），是我们自己封的 |
| 6 | 加减速 Δt = "ms/RPM" | ⚠️ 只在**速度模式**近似成立；力矩/电压模式的 LSB 是 0.1 A / 0.1 V |
| 7 | 低压保护 `data[6]` 填 0 就行 | ❓ 0 的含义未确认。厂家上位机默认 **24 V**、限 10~60 V |
| 8 | 无参数读写 | ✅ 对的（现在有源码级证据）|

### 7.1 我怀疑当初为什么把扭矩模式测"没成功"

扭矩模式的值是 **A×10**。如果照速度模式的习惯发个 `20`，那实际只有 **2.0 A** ——
200+ kg 的车根本不会动，于是被当成"这个模式不存在"。
**这是个很典型的量纲误判**，值得记着。

## 10. ❓ 仍未确定 / 必须实机验证

1. **扭矩模式在我们这台 FOC_CH4-V1.2 上到底能不能动作** —— PDF 和上位机都只是*声明支持*。
   厂家的 ESP32 参考固件里也**从未用过**扭矩模式（`control_mode` 只赋过 5）。
   **必须台架实测**：`mode=4, ctrl=1, 值=30`（=3.0 A），看回码转速/电流，
   以及**用手推得动吗**（= 有没有保持力）。
2. **模式 2 / 3 是什么** —— 厂家全代码从未赋值，**不猜**。
3. **E603 的 `DATA0`** —— 厂家上位机也把它丢掉了，只有 PDF 说它是固件大版本号。
4. **`data[6]` 低压保护：0 是什么意思** —— 关掉保护？还是用驱动器存的值？
   ★ 这可能解释过去几次"莫名其妙停下"：如果驱动器里存着 24 V，
   而我们的 24 V 电池跌到 22.8 V，它就会报欠压（码 7）而停机。
5. **电池上报的真实频率** —— PDF 默认 0.2 Hz，我们 README 写 1.8 Hz，两者对不上。
6. **PDF 自身三处矛盾**（别当限值用）：
   - 回码 DATA2-3 写 `int16(-300~300)`、控制帧写 `-500~500`、上报帧写 `-5000~5000`
   - 模式域写 `Uint8(0~5)` 却列了 `06：位置模式`
   - 控制字域写 `Uint8(0~2)` 却列了 `03`/`0F`
   厂家上位机的速度表满量程按 **500 RPM** 画，所以 `-300~300` 那处最可能是笔误。
